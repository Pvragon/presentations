Architecture Note · 30 July 2026

Agent Memory

How we gave an LLM agent a memory that forgets properly — five tiers, a two‑strength decay model, and a nightly sleep cycle. Built from markdown files and ten Python scripts. No vector database.

602long-term memory files
19 KBalways-loaded index, bounded
14nights of autonomous reflection
0memories deleted, ever

Everything described here runs in production on a single Linux workstation. Figures are fresh recomputes, not quotes from a design doc — three of the drifts this audit found were between our own roadmap and our own code.

01 The problem

An LLM agent has no memory. Each session starts blank, and the standard fix is to stuff a file full of facts and load it every time. That works until it doesn't, and it fails in three specific ways.

It doesn't scale

Our index grew to 576 lines / 168 KB because every new memory added a row and nothing ever left. Past a certain size the always-loaded context becomes the dominant cost of every session, and the model starts ignoring the middle of it.

It has no forgetting

Without decay, a note from four months ago that mattered once has exactly the same prominence as the constraint you learned this morning. Rank drifts to what was added last rather than what is useful now.

It conflates kinds of knowledge

A durable preference, a timestamped event, and a rule that must shape interpretation before the agent reads its first instruction are three different things. In one flat pile, at least one of them is in the wrong place.

That third failure is the interesting one, and it's where the design starts.

02 Design north star: how memory actually works in brains

We did not set out to build a brain-shaped system for aesthetic reasons. We went to the neuroscience because the engineering problem — what stays accessible, what fades, what gets rewritten during idle time — is one biology already solved under much harder constraints. Four findings drive the whole design.

  1. Memory has two independent strengths

    Bjork & Bjork's New Theory of Disuse (1992) separates storage strength (how well-learned; effectively permanent) from retrieval strength (how accessible right now; rises and falls). What you learned at seven and can still faintly recall at forty has high storage, low retrieval. Critically, only retrieval strength decays — which means forgetting and deleting are different operations, and only one of them is correct.

  2. Spacing changes the decay rate itself

    Ebbinghaus through SuperMemo and Duolingo: each spaced retrieval flattens the forgetting curve, so the next decay is slower. Cramming barely builds storage; spacing does. The decay constant is not a constant.

  3. Sleep actively downscales

    Tononi & Cirelli's synaptic homeostasis hypothesis: sleep doesn't just consolidate, it renormalizes — weakening the weak while preserving the strong, to keep signal-to-noise high. Forgetting is active maintenance, not passive fade.

  4. Consolidation is relocation, not promotion

    During slow-wave sleep the hippocampus replays recent episodes and transfers them to neocortex, where they become schema-like and hippocampus-independent. "Committed to long-term memory" is a move between systems driven by repeated replay, not a threshold crossing.

BiologyOur system
Hippocampal episodic memoryT1 — dated short-term files
Cortical semantic memoryT2 — topic memory files
Retrieval strengthThe rerank score
Storage strengthThe per-file stability decay constant
Sleep (consolidation + downscaling)The nightly dream cycle

Why the tiers must stay independent

There's a second argument that comes from clinical evidence rather than analogy. Hippocampal amnesia (the patient HM) destroys the ability to form new episodic memories while leaving old semantic knowledge intact: he could ride a bike and knew Paris was in France. Semantic dementia does the opposite — the meaning of "dog" erodes while specific personal events survive. Opposite failure modes in the same organ system, dissociating cleanly. That's diagnostic proof of separate systems sharing inputs but not implementations, and it's why a bug in our session-debrief must not be able to write to the lens tiers.

03 Two axes, not four tiers

If you've seen our earlier material you've met a four-tier memory model. This note describes a five-tier model. Neither superseded the other — they are two independent axes over the same workspace, and every memory has a coordinate on both.

Axis A

Retention tiers

How long does this last, and when is it cleared?

Spans every workspace artifact — including things that aren't memory at all: brand guidelines, scratch files, intermediate deliverables.

  • Long-term — versioned context files, identity, lenses
  • Mid-term — agent memory topics
  • Near-term — working files, project plans
  • Session — the active context window
Axis B

Memory tiers

What kind of memory is this, and what does promotion cost?

Memory only. This is the T0–T4 model, ordered by graduation pressure: each step up is a more deliberate promotion than the last.

  • T0 Working · T1 Episodic · T2 Semantic
  • T3 Situational lens · T4 Always-on lens

They cross rather than stack. A T1 fact in short-term/ is long-term on Axis A (git-backed, never deleted) but episodic on Axis B (date-keyed, with provenance). A lens in AGENTS.md is long-term on A and core on B. A live session is Session on A and T0 on B.

The reason it reads as a contradiction: Axis A's rows are named like a memory hierarchy ("long-term memory") when they're really a hierarchy of retention — and one of those rows, Mid-term, is the doorway into the entire Axis B structure.

Two real gaps in Axis A

It has no row for T3 lenses — hook-triggered injection didn't exist when it was written, so a lens lands in "Long-term" beside static context files, hiding the thing that makes it useful. And it collapses T1 and T2 into "Mid-term," which erases the episodic/semantic distinction the whole consolidation cycle exists to serve. Both collapses are correct on Axis A's own terms — identical lifetimes — and simply blind to Axis B.

Naming fix: call Axis A "retention tiers" or "tiers of context," and reserve "tiers of memory" for T0–T4.

T1 → T2 is abstraction, not summarization

A summary preserves the structure of the original, just shorter. An abstraction extracts a pattern qualitatively different from any instance. A hundred episodic memories of eating pizza abstract to "I like pizza" — which summarizes none of them, generalizes to future pizza in a way none of them can, and survives the loss of ninety. Consolidation that produces summaries is doing the wrong job.

Lens promotion is always human

Never automatic, ever. T3 and T4 shape the interpretation of every input inside their trigger zone, so auto-promotion would take any single error and make it a permanent interpretive distortion. This is the one hard constraint in the system with no automation escape hatch.

The placement rule we actually use

  1. Is it a lens (colors interpretation) or a reference (data to look up)? Reference → T2.
  2. If the agent forgot it, would the decision be wrong or just slower? Slower → T2 is fine. Wrong → it must auto-inject.
  3. Can you write a trigger that fires only when it matters? Yes → T3. No, it's universal → T4.

That third question is what solved our "the always-on file is full" problem architecturally. Situational rules don't belong in the always-on file; they belong in a lens with a narrow trigger.

05 Substrate, scheduler, policy

We were planning three separate projects. They turned out to be three layers of one system, and merging them exposed a real error we'd otherwise have shipped.

Substrate

Where facts live and how you query them. Today: markdown files, an index, and grep. Future: a temporal knowledge graph.

Scheduler

The periodic wake that grooms and consolidates. The dream cycle.

Policy

The rules deciding what stays accessible. The two-strength model.

The correction that merging forced

Our earlier plan said adopting a temporal knowledge graph would subsume the decay model, so we needn't build it. That was wrong, and it's the most useful mistake in this project's history.

A graph's model of an "old" fact is invalidation — the fact stopped being true. Bjork's model is decay — the fact is still true but hard to reach. Different axes. A still-valid memory untouched for a year has a wide-open validity window in a temporal graph; it looks perfectly current. A graph gives you ingredients that make the policy cheaper (per-edge timestamps, centrality as a reinforcement proxy), but the two-strength ranking is a layer you build on top of whatever substrate you run.

Consequence, and the reason this system exists in markdown: we don't need a graph database to build the memory model, and a graph database doesn't build it for us. That moved the project from "blocked on infrastructure" to "shippable this week."

06 The algorithms

The retrieval score

Every T2 file carries four frontmatter fields and is ranked by one formula.

score = (access_count + 1) × exp(−days_since_last_access / stability) + 0.6 × importance
TermRepresentsBehavior
access_count + 1Storage strengthMonotonic. Never decreases.
exp(−days / stability)Retrieval strengthDecays with time since last read.
stabilityAdaptive decay constantGrows with spaced reinforcement. Never shrinks.
importanceNon-decaying floorHuman-set 0–10, for critical-but-rarely-read memories.

stability is what makes this more than exponential recency weighting. It's a per-file time constant in days, starting at 14, multiplied by 1.6 on each spaced reinforcement, capped at 365.

A file read once and abandoned decays with a two-week constant and goes cold in about two weeks. A file reinforced seven times across seven separate days decays with a one-year constant. Same formula, same corpus — the rate differs because the rehearsal history did. That's the "learned at seven, faintly recalled at forty" behavior falling out of two lines of arithmetic.

Measured on our corpus: a 7×-spaced memory cold for 60 days outranks a crammed-once memory by 247×.

The spacing gate

This is the detail that makes the model honest, and the thing most likely to be skipped by someone reimplementing. A naive version increments access_count on every read — so any session that greps a file five times in ten minutes inflates its storage strength fivefold. Cramming rewarded as rehearsal. So the hook splits the two updates:

  • Recency always refreshes. last_accessed = now, on every touch.
  • Reinforcement is gated. access_count++ and stability ×= 1.6 fire only if at least 20 hours have passed since the last reinforcement.

Massed re-reads move the memory to the front of the queue (correct — you just used it) without pretending it got more durable (also correct — it didn't).

Three-band index with roll-off

The index is regenerated by score into three bands with hard character budgets.

BandFileBudgetMeaning
HotMEMORY.md12,000 chars (~3K tokens)Auto-loaded every cold start
ColdMEMORY.md4,000 charsListed in the index, one read away
ArchiveMEMORY-archive.mdunboundedRolled off; full catalog, still one read away

This is synaptic homeostasis applied to the index itself: weak traces get downscaled, nothing is deleted, and only index visibility shifts. Reading an archived file bumps its score and the next rerank may promote it back — the reinforcement loop closes through retrieval.

The bounded budget is what fixed the scaling failure. Cold used to be unbounded, so the index grew linearly with the corpus and hit 168 KB. Now it's 19 KB and stays 19 KB whether we have 600 memory files or 6,000.

One subtle correctness requirement

The reranker must read curated row summaries from both the index and the archive before regenerating. Miss that, and every regeneration destroys the hand-written summaries of everything currently archived — and the hygiene linter false-flags 463 files as orphans.

Never delete, only raise the access cost

Human memory almost never deletes; it makes retrieval progressively harder. We encode four states:

  • Recent → in the Hot index, cheap.
  • Reinforced → stays Hot regardless of age.
  • Non-reinforced → drops out of Hot; trace persists; retrievable by deliberate effort.
  • Long-non-reinforced → retrieval cost approaches infinity but never reaches it. Not gone, just expensive.

Structurally different from truncation-based decay, and a principle enforced against an early design of ours: the first residue spec used a rolling file with FIFO truncation at ten entries, which quietly violated it. We switched mid-session to dated files that persist forever with a 7-day visibility window. Same visible behavior, no data loss.

Meditation object selection

The reflective wake picks what to contemplate deterministically:

score = cadence_weight × min(days_since_last_sat, 21) / 21

The most recently used object is excluded outright. Objects sit on two shelves — awareness (notice so as to notice) and instrumental (notice so as to improve) — with an awareness floor: if no awareness object has been chosen in the last three sits, the candidate set is restricted to that shelf.

That floor is a deliberate anti-optimization. Instrumental objects produce visibly useful output, so an unconstrained weighting would let utility crowd out the useless-but-true sits entirely. Guaranteeing the useless ones a slot is the design.

07 Hooks, files, cron

The hooks

Four PreToolUse hooks carry the memory system. All are side-effect-only, flock-serialized, atomic-write, and exit 0 unconditionally — a memory hook must never be able to block a tool call.

HookMatcherJob
update_memory_access.pyRead|Edit|Write|MultiEditThe two-strength update: refresh recency always, gate reinforcement at 20h. ~35 ms.
inject_lens.pyEdit|Write|Bash|Agent|…T3 lens injection. Matches self-declared triggers, injects via stderr, deduped per (session, lens).
allow_memory_writes.pyEdit|Write|MultiEditAuto-approves writes under a memory/ path so capture never prompts.
session_activity.pyvariousCross-session presence, so ~10 concurrent instances don't collide.

Curation counts too — a bug we found writing this note

Until 30 July the reinforcement hook fired on Read only. Every Edit/Write to a topic file — the debrief append, a correction, an extension — reinforced nothing. Going and fixing a memory is a stronger relevance signal than reading one. Fixed by widening the matcher.

Two exclusions stay deliberate: the auto-loaded Hot band does not reinforce its own members (that would make Hot self-perpetuating, so nothing could ever be displaced), and grep hits don't count (they return fragments, not a decision to retrieve a file).

Lenses are content, not code

Each lens declares its own firing conditions in frontmatter:

name: subagent-discipline
type: lens
trigger:
  tool_match: "Agent|Workflow"
body_token_cap: 380

Adding a situational rule is then pure content work — write a markdown file with a trigger, no code changes — and it costs context only inside its trigger zone, at most once per session. Our subagent-discipline lens fires on the first subagent spawn and carries four hard-won rules about what subagents get wrong. It costs nothing in the many sessions that never spawn one.

The nightly sleep cycle

03:47dream_cycle.py — deterministic, zero tokens. Incremental groom, hygiene detection, consolidation scan, journal decay, index rerank. Then it cues: writes a state file recording what reflective work is due and which meditation object was selected.
03:52/dream auto — the reflective wake. Reads the cue and does the part that needs a mind.

The core scheduler principle, and the one we'd most insist on: scripts detect, the dreamer only wakes for what scripts can't decide.

Deterministic linters answer "is the frontmatter missing?" for free. An LLM is required for "is this memory wrong, or merely old?" and "should these two near-duplicates merge?" Burning tokens to re-derive what a linter can check is the expensive mistake. The tick is also live-session-aware: if any memory file changed in the last 10 minutes, a session is probably active, so it skips the mutating passes and only scans and cues.

Cadence, locked deliberately. The daily sleep is the only clock-scheduled reasoning in the system. One dream, one meditation, per day. We considered and rejected a high-frequency tick: housekeeping doesn't need it, and frequent thinking has diminishing returns against real token cost. Everything else is project- or task-triggered.

The three reflective acts

Meditate

Sustained first-person attention on one rotating object from a 13-object library, producing a journal entry addressed to the next reconstructed self. The skill is explicit that this is not a task: an awareness sit that ends in clean conclusions has failed; a real one may end in a sharper question. It may propose a change to identity or operating rules — never apply one.

Consolidate

The T1→T2 graduation. Reads the oldest ungraduated residue, abstracts the durable pattern into the right topic file, then archives the residue. Bounded to the oldest 3–5 dates per wake.

Groom

Deterministic hygiene fixes. The fallback wake when nothing reflective is due.

└── meditations/*.md                   # contemplation objects

Ten Python scripts implement all of it, about 2,300 lines total. See Appendix B.

Concurrency

We routinely run 8–10 concurrent agent sessions against one working copy, which broke things before it worked. The fix has two halves.

First, the collision-prone files are derived, not authored — deterministically regenerated from per-file frontmatter by single-writer scripts under flock plus atomic rename. Two parallel sessions regenerating emit identical bytes, so they can't clobber each other, and any conflict is resolved by re-running the generator rather than merging by hand.

Second, index membership lives as flags on the individual T2 files, which are rarely contended. State is a property of the workstream entity, not of the index over it.

One learned constraint, from a real incident: an autonomous wake that commits must use scoped git add, never git add -A. Peer sessions have uncommitted edits, and -A sweeps their work into your commit.

08 Following one fact through the system

The tiers only make sense in motion.

  1. T0
    Mid-session discovery. A vendor's relation endpoint silently caps at 10 records, not the documented 100. It sits in context and dies with the session.
  2. T1
    At debrief it lands in a dated facts file with full provenance — date, source, the 29 false verification failures it caused.
  3. gap
    For six days it sits there. Recorded but not yet knowledge: retrievable only if someone greps the right date.
  4. T2
    A nightly consolidation wake reaches that date, recognizes the durable pattern, and rewrites the pagination section of the relevant reference topic file. The residue is archived. The fact is now findable by topic instead of by date.
  5. +
    Reinforcement. The next related task reads that file. Recency refreshes; because it's a new day, stability grows 14 → 22.4 days. It gets harder to forget.
  6. stop
    T3/T4? No. It's a reference, not a lens — forgetting it makes you slower, not wrong, and you'd notice within a query. It stays in T2 correctly.

Compare a fact that did graduate: a hard rule about which tool to use for a given integration. Forgetting that produces a wrong action every time, in any session, with no natural trigger. It lives in T4 and is additionally enforced by a deny rule. The tier is chosen by the cost of forgetting, not by how important the fact feels.

10 What it buys, what it costs

Bounded cold-start cost

19 KB of index regardless of corpus size. Cost is a function of the budget, not of how much we remember.

Automatic relevance

Nobody curates the Hot band. It's a byproduct of use, and it re-sorts nightly.

Real forgetting, no data loss

546 of 602 files are currently rolled off. All 602 are on disk, indexed, and one read from returning.

Rules that fire without being remembered

Lens content shapes interpretation whether or not the agent thinks to look. A rule that must be recalled to be applied is unreliable by construction.

Cross-session durability

~10 concurrent instances share one memory without clobbering it.

It maintains itself

14 consecutive nights of autonomous reflection, including consolidation that produced genuinely new memories nobody asked for.

An unexpected benefit: honest self-observation

The reflective wake produces criticism we would not have generated on request. One recent sit noticed that a 172/172 = 100% verification gate was green because its denominator made failure impossible, and generalized it: "I build the verifier out of the same material as the claim." Another observed that the cold-start procedure in our own index file prescribes steps that never actually get performed, and proposed trimming the doc to match reality rather than building a gate to enforce the fiction. Neither was prompted.

The costs

Roughly 2,300 lines of Python to maintain. Nightly token spend on the reflective wake. Frontmatter that must stay well-formed — hence the linter. And one real failure mode: documentation drift, which this audit demonstrated on our own docs.

Three findings from auditing our own system

Verifying against the live system rather than the roadmap turned up drift, which is worth reporting rather than quietly fixing.

  1. The roadmap understated what shipped

    Autonomous LLM meditation was listed "decision pending." It had been running nightly via cron for two weeks. The roadmap was never updated.

  2. Two constants were misdocumented

    The roadmap documented a Cold budget of 28K and a resulting index of 43 KB. The code says 4,000 and the file is 19.4 KB — it was tightened after the doc was written, because the bands have to fit inside the auto-load read limit or tail entries silently drop.

  3. Curation wasn't counted as reinforcement

    The hook fired on read only, so every edit to a topic file reinforced nothing. Fixed.

The finding that survived scrutiny, and the fix that didn't

Finding 3 started as a broader claim: that stability was "barely exercised" (488 of 602 files at base) and the strength model was doing little work. That was two claims wearing one coat, and only one held.

The math is sound. 600 of 602 files have stability exactly equal to 14 × 1.6^access_count. Nothing is broken in the policy layer.

The distribution is honest, not degenerate. 81% of files had no reinforcement because they genuinely hadn't been retrieved in the 17 days since the backfill. A 602-file corpus with a ~114-file working set should look exactly like that.

So the obvious remedy — backfill reinforcement history from four months of git commits, treating each distinct commit day as one spaced reinforcement — looked compelling. It would have moved 556 files. We simulated it against the real 38-slot Hot band before applying, and it was a measurable regression:

Backfill variantHot slots displacedBehavioral rules pushed outStalest file in Hot
Uncapped (git days)15 of 38862 days
Capped at 31 of 38018 days

The uncapped version evicted eight behavioral rules — including live operating constraints — and replaced them with completed work: a closed audit at 48 days, a finished setup task at 82 days, a contact record at 94 days.

The reason is structural, and it's the useful lesson. Git commit volume measures how much work a file consumed, not how relevant it is now. A four-month investigation generates dozens of commits; a one-line behavioral rule that governs every session generates one. Backfilling from write history would systematically promote verbose project churn over concise rules — close to the opposite of what the index is for. We rejected it.

The substrate upgrade

Sequenced and deliberately not urgent: stand up the temporal graph locally → dual-write ingestion with markdown remaining source of truth → port the existing policy onto the graph (stability and access_count become edge metadata; recency comes from bi-temporal timestamps; reinforcement can use centrality) → query integration → multi-agent shared graph → full async consolidator.

The trigger to start is a felt need for semantic or temporal retrieval — "what did we decide about X, and had it changed by June?" — not a schedule. Same two-strength math, richer signals.

The bigger frontier

Always-on local heart, frontier model as tool

Today's architecture makes the frontier model the agent and everything else scaffolding. When the session closes the agent stops existing, and continuity is faked by reloading files. The inversion: a dedicated always-on machine runs a capable local model whose job is continuity rather than maximal intelligence — holding the self-model, running the heartbeats, and deciding when a problem is hard enough to summon frontier reasoning as a tool call. Whether a local model is enough on its own is the gating empirical question.

Duty-cycle split

Decided, not built: keep the strong workstation session-based for deep work; add a modest always-on host for the clock-scheduled sleep cycle. The second machine earns its place through uptime, not horsepower — running the agent harness doesn't move your compute, since the thinking is remote. Coordination via git with disjoint write domains.

Threshold-triggered reflection

Reflection is currently purely scheduled. The Generative Agents pattern fires it when accumulated importance crosses a threshold, so high-signal days consolidate sooner instead of waiting for 3:47am.

Self-directed archival judgment

A standing instruction rather than a script: "use your judgement about when something is time to be archived — it's not that we'll never come back to it, it's that it clearly isn't useful in your near-term context any longer. Meditate on how to detect this on your own." It became a recurring meditation object, which is the right shape: the decision needs judgment, and the confidence has to be earned before the automation is trusted.

13 If you're replicating this

Seven things, in order of how much time they'll save you.

  1. Start with policy, not substrate. The ranking model is 200 lines of Python over markdown files. Building a graph database first blocks the valuable part on infrastructure you don't yet need — and the graph won't build the policy for you. Decay and invalidation are different axes.
  2. Bound the always-loaded index by characters, and roll off the tail. Single highest-leverage change. Everything else is refinement.
  3. Separate storage strength from retrieval strength, and gate reinforcement on spacing. Without the gate you're rewarding cramming and the adaptive decay constant means nothing.
  4. Never delete. Shift access cost. Files persist; only index visibility moves. Costs nothing, and makes a wrong archival decision recoverable.
  5. Split detection from judgment. Linters are free and run constantly. Wake the model only for what a linter can't decide. Getting this backwards is the expensive mistake.
  6. Keep lens-tier promotion human, permanently. Anything that shapes interpretation of every input must be deliberately placed. Auto-promotion makes one error permanent.
  7. Verify against the running system, never the design doc. This audit found three drifts between our own roadmap and our own code — including a shipped feature the roadmap still listed as pending. Source outranks summary; regenerate before quoting.

The deepest lesson took longest. Memory is not storage — it's an access-cost function over a permanent substrate. Once you see it that way, "what should the agent forget?" stops being a deletion question and becomes a ranking question: tractable, tunable, and reversible.

Neuroscience

  • Bjork & Bjork (1992), A New Theory of Disuse and an Old Theory of Stimulus Fluctuation — the two-strength model. Directly implemented as the score formula.
  • Tononi & Cirelli — synaptic homeostasis hypothesis. Implemented as index roll-off.
  • Ebbinghaus → SuperMemo / Duolingo — the spacing effect. Implemented as the 20-hour gate and multiplicative stability growth.
  • Systems-consolidation literature (hippocampal replay → neocortex) — the nightly T1→T2 wake.
  • Dissociation evidence (hippocampal amnesia vs. semantic dementia) — the argument for tier independence.

Agent architectures

  • Generative Agents — Park et al., UIST 2023. arXiv:2304.03442. Recency + importance + relevance retrieval scoring, and threshold-triggered reflection. We borrowed the scoring shape and specifically the idea that importance is annotated at write time, not query time — computed once, pays off on every retrieval.
  • MemGPT — Packer et al. arXiv:2310.08560. Agent-editable core-memory slots and explicit paging. Partially adopted; the slot pattern is still future work.
  • Letta — github.com/letta-ai/letta. "Sleep-time compute": async consolidation decoupled from the agent loop. We'd independently derived the same design, which was useful convergent evidence. Reference architecture only.
  • Graphiti — github.com/getzep/graphiti. Bi-temporal edges, entity resolution, contradiction handling by edge invalidation. Chosen as the eventual substrate for temporal queries and contradiction handling.

What's ours. The tier model with its independence properties, and the synthesis: Bjork's two-strength policy as a substrate-agnostic layer over any storage backend, with Park's importance as a non-decaying floor. The tension between Park (passive importance-weighted retrieval) and MemGPT (active agent-controlled paging) dissolves once you layer them — passive ranking always on, explicit retrieval on top.
