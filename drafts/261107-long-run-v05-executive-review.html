v0.5 rebuilds the harness around one repeating building block, and takes the question “are we converging?” away from the session doing the work. Nothing is built yet; the recommendation is to build level 1, the first proving step (three bounded runs), and judge again from what they show.

The goal is a harness that can run a business for weeks

Jaime’s test case is open-ended: “you are the CEO of a printables business … earn as much revenue as you can.” A goal like that never finishes. It has to be broken into products, channels and operations, each still too big for one Claude session, and it has to hold its direction for weeks while the work underneath changes.

Today’s harness, v0.4, turns a plan into a queue of work. Owner sessions build each piece, automated gates test it, and the CEO pane (the Claude session that launched the run, not Jaime) decides what comes next. This week it ran eleven goals, five of them on Deckwright, the Magic: The Gathering deck builder.

This week’s runs passed fast, then never finished

Every run did its first pass quickly and cheaply. Then the second pass ate the run: Deckwright finish built all its pieces on 21% of its tokens and spent the other 79% on rework that never converged (week synthesis). Five things went wrong, each built into how v0.4 works:

  1. Fixes were treated as new work. A one-line fix went back through spec, review, build and gate, as if it were a new feature.
  2. The definition of done kept changing. Done included a walk, a session that uses the product as a user would and lists problems. The walk was capped at five problems and nearly always found five, so it could never come back clean.
  3. Nobody owned the architecture. Planning worked down the issue list and never decided which module owns what. On Deckwright, card reading spread across ten packages and fixes went card by card.
  4. Coordination ate a third to half of the tokens (review 3): the CEO pane, dispatch, reviews and retries.
  5. Nobody watched convergence or forced a rethink. The CEO pane ran the work and also judged its own progress. On close-all it spent hours tuning a design Jaime had already ruled against.

Jaime put the last one as a question: “what’s watching convergence signals and demanding a judicious reframe?”

The node and how nodes stack

A node is a record on disk with four parts: a goal, the slice of the overall plan it serves, a finite set of exit tests (pass-or-fail checks that define done for that node), and a budget. Every node runs the same procedure:

  1. Test. Run the exit tests. If they all pass, the node is done and reports one status line to its parent.
  2. Recognise. If a test fails and the node already has an owner session assigned, code sends the failure straight to that owner.
  3. Split. If no owner fits, or the same tests fail again, a planner divides the node into a few child nodes, one per failing area.
  4. Commit. Only the next child is fully specified and started. The rest stay one-line stubs until needed.

Because a node can hold nodes, the block stacks. A business is a node whose children are Product, Channels, Operations and Finance; Product holds a catalog line; the catalog line holds tasks. A long run today is one branch.

Each product keeps one tree across runs

The tree lives in the product’s repository and outlasts any single run. A run starts on a product and a node, never on a fresh plan file, so later work always re-enters the same tree. Finished parts keep their identity and their tests, and become the regression suite for whatever comes next.

When strategy and tasks are planned

Jaime’s planning ladder has five levels: the want, the capabilities, the data sources, the processes and architecture, and the tasks. The first four are the frame. It is written in full before building, kept short, and carried in every session’s brief. Only the tasks wait until work meets reality.

This answers Jaime’s drift challenge: “What is holding the end goals and capabilities in its mind and really answering every decision and planning every step with them in mind?” The frame does, on disk, instead of the CEO pane’s memory.

Claude, Jev and code

Every step is done by one of three kinds of actor:

  • Claude, for judgment. The strategic planner writes the frame. Node planners write specs and splits. Owners build. The walker uses the product. The gate reviewer judges architecture changes. The decider rules. The CEO pane talks with Jaime.
  • Jev, for closed questions. Jev is a typed decision model for yes-or-no questions such as “is this the same failure as before?”. Its confidence is not calibrated yet, so it arrives at level 2, after replay on old logs.
  • Code, for everything mechanical. Dispatch, brief assembly, routing failures to owners, running every test, merging, watching the signals and recording rulings. Code spends no tokens and is not tuned by a model.

The CEO pane proposes: requests, priorities and appeals. The decider rules: a fresh Claude session that decides as Jaime would, from the frame, his recorded rulings and evidence that code assembles. Code enforces: only the daemon (the program that runs the loop) can record a ruling, and it refuses one from any other session. Jaime signs the want: the top of the frame changes only by his own typed words. Owners stay on Opus at level 1, so the test of the node design is not mixed up with a change of the model that builds.

Every session starts with the right expertise

Each brief is assembled in code from two packs. A role pack says how to do one kind of work: architecture planning, coding, data analysis, research. A domain pack holds the domain’s own stages, rules and test style, such as get, clean, analyze and publish for billing. A study of 14 past episodes found that work succeeded when it followed the domain’s own stages and failed on a generic breakdown (staged-thinking study). Packs are size-capped. From level 2, what a project learns that holds beyond it moves into its domain pack.

From goal to first release, step by step

  1. Intake. Jaime states the goal. The strategic planner grounds itself in the existing code and data and, for a product that reads an outside format (Deckwright reads the card scripts of Forge, an open-source rules engine), lists every construct that format contains.
  2. The strategic pass. The strategic planner writes the frame: want, capabilities, data sources, and the architecture, meaning the modules, one contract between each pair, and where each kind of interpretation may happen. Architecture rules become tests. Jaime signs the want and capabilities; the decider signs the rest.
  3. The matrix. A dedicated planning session writes version 1 of the coverage matrix, a grid of test cases that defines done. For Deckwright each cell is a card effect with a real card and an expected answer taken from judge rulings and official sources, never from the owners who must pass it. The decider checks a sample before it is frozen.
  4. Nodes plan just in time. Code starts the first child of the root. Each node specifies only its next child.
  5. Building. Owners build their nodes on separate branches. Code merges in a parallel merge train: several finished pieces are verified at once and land one after another in seconds. Speed is a core metric (Jaime: “execution speed is a core metric of the system”), so slow verification counts as a defect to fix.

Branches are kept from overlapping by design. In past runs, owners edited the same files and the clashes showed up only at merge time, where they cost the most. In v0.5 the strategic pass gives every file exactly one owner, and a file everyone needs is split into one piece per owner. When a node splits, each child lists the files it will write, and code refuses a split where two lists overlap: those children run one after another or become one. An owner cannot write a file outside its list; it asks that file’s owner instead. Code also compares the open branches as work goes on and pauses one that is heading for a clash before more work piles onto it. A clash that still happens counts as a planning mistake against the split that allowed it. 6. Testing. Every merge runs its node’s tests and every architecture test. Where today’s code already breaks an architecture rule, the test works as a ratchet: a merge fails only if it adds a violation. 7. The fix wave. Code runs the whole matrix and sends every red cell to its owner in one batch, with no new spec. 8. The walk. When the matrix passes, one walker uses the product and writes down every problem it finds. 9. Acceptance. The decider sorts the list. A problem showing that a test was wrong is fixed in this release. A new kind of problem becomes a cell of the next version. The decider accepts the release; the CEO pane cannot.

When things go wrong, the response climbs one step at a time

The governor is code that reads the run’s event log after every fix wave and every hour, looking for signs of a stall, such as fix waves that stop turning failures into passes. It escalates in order:

  1. A test fails. Its owner fixes it.
  2. A node stays stuck past its budget or over two cycles. Code launches a node planner to re-plan that node.
  3. The same failure shows up in many places. Code pulls the fix up to the node that owns that kind of failure, so it is fixed once at the root.
  4. No node owns it, or the re-plan fails too. The plan itself is wrong. The governor wakes the decider, which reframes the architecture. Its verdict binds: work it touches stops until the change is made, and every reframe names the work it removes or redraws.
  5. The want itself is wrong. In runs Jaime owns, he rules. Otherwise the decider rules with a recorded default that Jaime can reverse at his daily review.

The Forge night shows the ladder at work. Under v0.5 the frame names the card-schema module as the only place card text is read, and a ratchet test enforces it on every merge, so a task that adds a new card-text reader fails at once. If misreads still cluster, step 3 sends them to the module that owns them. If no module does, the decider adds the missing central process, “Forge construct encoding”, and per-card fixes stop until it exists. This applies Jaime’s rule: “fix a problem at its root in a way that the solution will apply to the project as a whole.”

The system watches efficiency, not just convergence

A run can converge and still cost far more than it should. Jaime: “We really do need controls in place that catch not just convergence but poor implementation decisions that drive up token use, rereviews of known good work, … anything that drives up execution time and token use unnecessarily.” One measured Deckwright session showed why: a third or more of its spend was avoidable, almost all of it inside the building work itself, where no convergence or overhead check was looking (usage forensics). Most of it came from long-lived workers re-reading an ever-growing conversation.

So v0.5 prevents waste by design first and watches for it second:

  1. Short sessions, sized to one batch. Each piece of work is cut small enough to finish in one compact session, and the session ends when its work is committed. If a session grows too large anyway, code stops sending it work and starts a fresh one at its next commit.
  2. Known-good work is never re-checked. Code remembers every test result and review by the exact content it judged, so work that already passed is not tested or reviewed again. Owners run targeted builds and tests, not full rebuilds.
  3. Cost per landed result is tracked. The board shows what each finished, merged result cost, beside throughput. A session that spends heavily and lands nothing is stopped, and a part of the tree that costs far more than the rest is re-planned.
  4. The CEO pane is not woken by chatter. Only rulings, appeals, verdicts and releases wake it. Owners run as separate sessions the daemon launches, so their routine status messages never reach it.

When Jaime changes course, the change re-enters the tree

Any request, from Jaime or the CEO pane, is a proposal. The decider classifies it and picks where it enters:

  1. A priority change reorders work only. The CEO pane writes it and code checks that nothing else changed.
  2. New scope under existing capabilities enters at the lowest node that covers everything it touches. That node’s architecture tests run again, and the added cells go into the next matrix version within a scope limit.
  3. “That went well, now do Y and Z” is an expansion: it changes the want or the capabilities. Jaime sees the change to the top of the frame and signs it. The strategic planner then re-tests the existing architecture against X plus Y and Z on the code as built and rewrites only the parts that fail. X’s accepted cells become regression tests. The run’s history carries over, so an expansion cannot silence a governor that was about to fire.

In v0.4 added scope joined the same queue; on contract invoices it took 63 launches to land 3 pieces after the first release (week synthesis).

The harness improves only between runs

A run improves the work, never its own rules. The harness version is frozen for the length of a run. Between runs:

  1. Every confirmed harness fault becomes a regression test before the next version.
  2. One change ships per version, and a bad version is rolled back by pinning the previous one.
  3. Every session records which prompt and packs it loaded, so an outcome can be traced to what it saw.
  4. From level 2, a model proposes one change at a time with a prediction, and a frozen replay of past runs judges it. Rowan merges defect fixes; changes to done, thresholds or the evaluator need Jaime’s ruling.

Thresholds, cost and scale are still unproven

  • The governor’s settings come from one week of runs. Replayed, it would have warned on the two worst runs many hours before anyone noticed, but it missed one, and nothing was held out (governor backtest). Level 1 treats every setting as a starting value.
  • The cost figures are a model. The spec estimates that coordination falls well below this week’s share; the first level-1 run gives the first real number. The efficiency thresholds rest on one measured session.
  • Speed is a target, not a measurement. The merge train and faster builds are meant to make a stall visible within a few hours. Whether a real run gets there is open until level 1.
  • Business scale is unproven. No published system shows a general planning procedure running an open-world goal for weeks, so the design claims only that the node stacks in principle.

Proof runs level by level, starting with bounded builds

  1. Before level 1, a replay. Run the governor over this week’s logs.
  2. Level 1, bounded builds. Three runs: finishing Deckwright as the first entry of its tree, a run in a domain with no pack yet, and a small goal that is accepted and then expanded. Pass means releases accepted without redefining done, and the expansion re-entering through the decider. If two runs fail to converge, fix the design.
  3. Level 2, a product. A multi-level build like the billing reconciliation work; Jev and the between-runs improvement loop start here.
  4. Level 3, always on. One shop on real revenue, with a gate on irreversible outside actions such as spending, publishing or contacting customers. Jaime’s interventions should fall over time.

Five decisions for Jaime, each with a recommendation

  1. Is the node the right building block? One record with goal, plan slice, exit tests and budget, running the same four steps at every level. Recommend: yes; it is the one piece that stacks from a task to a business.
  2. Is “strategy up front, tasks just in time” right? The frame is written in full and held; tasks wait for reality. Recommend: yes; it answers the drift challenge without over-planning tasks that change anyway.
  3. Is the separation of powers right? The CEO pane proposes, the decider rules, code enforces, Jaime signs the want. Recommend: yes; this week’s worst hours came from a CEO pane judging its own progress.
  4. Is the context-pack model right? Every session gets a role pack and a domain pack, assembled in code. Recommend: yes, starting with a handful of packs frozen across level 1.
  5. Is the proving path right? Replay, then three bounded runs, then a product, then one shop. Recommend: yes; never the business first.
