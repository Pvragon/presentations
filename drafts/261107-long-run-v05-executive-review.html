v0.5 rebuilds the harness around one small loop that repeats at every size, and takes the question “are we getting anywhere?” away from the session doing the work. Nothing is built yet, and the recommendation is to build the first proving step (three bounded runs) and judge again from what they show.

Long-run is the harness that takes a goal and runs AI sessions for hours or days to plan, build, check and release work. v0.4 did each first pass quickly, then spent far longer on rework. On Deckwright finish it built 15 pieces in 5.3 hours and then reworked for 34. On waystar it spent 62 hours on one check of past billing history while the workbook Jaime wanted was never produced.

What you are being asked to decide (all in section 11) - Five choices about the design’s basic shape, each with a recommendation. - Six open questions that testing raised, each with a recommended default. - Five findings from an independent review that change the first proving step. - The items you already settled.

Terms

Who is involved.

  • Jaime (you): the owner.
  • Rowan: the AI assistant that operates the harness for Jaime.
  • CEO pane: the Claude session that launched a run and talks with you; it proposes, it does not decide.
  • Builder: an AI session that writes or fixes one piece of work.
  • Customer tester (the walker): an AI that uses the finished product as a customer would and lists problems.
  • Supervisor (the decider): a separate AI that never builds and makes the binding calls.
  • Watchdog (the governor): plain code that watches time, money and progress.
  • Jev: a trained model that answers one yes-or-no question many times, cheaply; not used until level 2.
  • Opus and Sonnet: Anthropic’s larger and smaller Claude models.
  • Tokens: the unit AI usage is counted in; a session’s context is the tokens it holds in view.

What the work is made of.

  • Piece (or node): one part of the job, with its own goal, its own pass-or-fail checks and its own budget.
  • Frame: the written big picture of the plan: the goal, the capabilities (the main things the product must be able to do), the data sources, and the architecture (which module owns which job).
  • Contract: the agreed hand-over format between two modules.
  • Checklist (the matrix): the frozen list of test cases that defines “done” for one version.
  • Version: a working result you can use; the next version adds to it.
  • Flat build: one builder plus one fresh reviewer, with no splitting into pieces.
  • Packs: short reference notes handed to each session: a role pack (how to do one kind of work) and a domain pack (the field’s own stages and rules).
  • Declared process: the written-down list of every step, who does it and the limit on every repeat; code checks it and draws the generated charts from it.

How work moves and is measured.

  • Branch: a builder’s private copy of the code; it joins the shared copy only after it passes.
  • Merge train: a line that checks several finished pieces at the same time and joins them one after another.
  • Check slots: how many of those checks may run at once.
  • 95th percentile (p95): the time that 95 of every 100 checks finish within.
  • Weighted tokens: AI usage counted so that a costlier model counts for more.
  • Cool-down: after an alarm fires on a piece, a quiet period before it may fire there again.
  • Regression test: a test that keeps a fixed problem fixed.
  • Shadow: running and recording, but changing nothing.
  • “Up to 2 tries” (charts): a piece that fails its checks twice is re-planned rather than fixed a third time.
  • “Up to 3 more times” (charts): after three more versions in one run, the supervisor reviews the plan before more is spent.

The proving levels. Level 0 replays old logs and tests the prompts; level 1 is three bounded runs; level 2 is a whole product; level 3 is one shop on real revenue.

1. Core principles

  • One loop at every size. A task, a product and a business all run the same steps: test, build or split, test again.
  • Done is a frozen checklist, written before building from outside sources by someone other than the builders, and it does not change during a version.
  • The deliverable comes first. What you asked for never waits on a check of history; such checks run beside it.
  • Start small. A bounded goal starts as one builder plus one fresh reviewer, and splits only when it outgrows that.
  • Plan the strategy up front, tasks just in time. The big picture is written once and carried in every brief; tasks are planned when work reaches them.
  • Separation of powers. The CEO pane proposes, the supervisor rules, code enforces, and you sign the goal. Your typed word binds at once.
  • Code runs everything mechanical. Routing, testing, merging and watching cost no AI tokens and are not tuned by a model.
  • Time and money wake the supervisor; counts do not. A failure count only triggers a local fix.
  • Speed is a core metric, and slow checking counts as a defect.
  • The harness improves only between runs. A run improves the work, never its own rules.

2. The core loop, step by step

Each version runs this loop once. Building happens in step 5 and only there; steps 1 to 4 decide what to build and how “done” will be judged.

  1. You give a goal. The strategic planner, an AI, reads the existing code and data first.
  2. It writes the frame: the goal, the main capabilities, the data sources and the architecture (which module owns what). It also lists the few big policy calls, such as which source wins, and asks you for each. You sign the goal and capabilities; the supervisor signs the rest.
  3. A planning session writes the checklist (it uses the builder prompt), each case with an expected answer from an outside source. The supervisor samples it, then it is frozen. Version 1 holds at most 300 cases.
  4. Code chooses the shape. If one builder can do it: one builder plus one fresh reviewer. If not, a planner splits it into pieces, each with its own list of files it may write.
  5. Build. Each builder works on its own branch, a private copy of the code, in a fresh session sized to finish one batch. When it hands back, code commits the work.
  6. Test. Code merges finished pieces in the merge train and runs each piece’s checks plus the architecture rules. For a large piece or a flat build, a fresh reviewer AI also reads the work. Work that already passed is never re-checked.
  7. Fix. Code sends every failing case back to its builder in one batch, with no new plan.
  8. Try it. When the whole checklist passes, one AI uses the product like a customer and lists every problem it finds, with no cap.
  9. Decide. The supervisor sorts that list: a wrong test is fixed now, a new kind of problem becomes a case in the next version. It answers a short release checklist (“does every capability still serve the goal?”), then approves or refuses.
  10. You get a working version. Only the supervisor’s approval releases it. The next version starts at step 3.

The watchdog reads every result. A failure count only triggers a local re-plan of one piece. If time or money runs on without progress, it wakes the supervisor, whose ruling can redraw the plan. A redrawn plan first tests what already works, then builds only what still fails.

3. How it nests

A piece of work can hold smaller pieces, so the same loop stacks from a single task up to a business.

  • A piece starts with its goal, checks and budget frozen, plus the slice of the frame it serves.
  • Test first. If every check passes, the piece is done and sends one status line up.
  • Build when it fits. If a builder owns the piece, or it is small enough for one, code sends the failure straight to that builder. This is where building happens, at every size.
  • Split when it does not. A planner AI cuts it into about five smaller pieces, each with its own checks and its own files. One planning session writes every child’s spec.
  • A parent’s plan becomes its children’s fixed inputs. Each child’s goal, checks and budget are frozen when it starts, and a child cannot change them. A child starts only when the work it depends on has passed its own checks. Children that write different files start together.
  • When a child finishes, the parent tests itself again or starts its next child.
  • Each product keeps one tree in its repository across runs. Finished pieces keep their checks, which become the safety net for later work.

4. Who does what

Colour Actor Does Examples

Purple Jev, a yes-or-no decision model closed questions asked many times “same failure as before?”; “retry, fix or re-plan?”

  • Jev is not used at level 1. Its confidence is not yet calibrated, so its questions are answered by simple code rules and replayed offline; it goes live only past an agreement level you set.
  • Rulings can only be recorded by code. No AI session can write one, and a ruling of yours counts only as a quote from your own typed message.

5. Where prompts are used

Every AI step is a fresh session that code launches with one prompt and an assembled brief. Prompts never call other prompts. There are eight prompts; one, the improver, starts at level 2.

Prompt Called when Model What its context holds
CEO pane you type; code wakes it for a ruling, appeal, verdict or release Sonnet your messages, strategy pack
Strategic planner start of a run, an approved expansion, a redraw verdict Opus the existing code and data, architecture pack, domain pack
Node planner a piece starts or must be re-planned Opus the piece’s record and failing tests, frame slice, packs
Builder a piece is dispatched; a failing case is routed back; checklist writing Opus at level 1 the failing cases, frame slice, coding pack, domain pack
Customer tester (walker) the whole checklist passes Sonnet a brief generated from the frame, so the CEO cannot steer it
Fresh reviewer a large piece lands; a flat build lands (reviews blind first) Sonnet the changed files, the contracts, packs
Supervisor (decider) a time or cost alarm; a request; a challenge; the try-out’s list; a sign-off Opus the frame, the record of past rulings, evidence code assembled
Improver (level 2) between runs not set yet the closed runs’ faults and events

Where each setting lives

  • In the prompt text: how to plan (real data first, one owner per file, about five children per split, a piece small enough for one session), the release checklist questions, how to sort the try-out’s findings, and output limits.
  • In the packs: a role pack (how to do one kind of work) and a domain pack (the field’s own stages and rules).
  • In the settings file (the declared process): every alarm threshold and cool-down, and the limit on every loop.
  • In code: pack size limits, the frame and checklist caps, context limits, model per prompt, merge budgets.
  • Recorded every launch: which prompt version and packs a session loaded, so an outcome can be traced back.
  • Tuned only between runs, one setting at a time, starting at level 2. Inside a run, the supervisor may only move a few settings within declared ranges, such as a cheaper model or smaller packs.

6. How nested levels plan and manage context

Planning at each level

  • The frame is planned up front by the strategic planner, at four levels: the goal, the capabilities, the data sources, and the processes and architecture. It is capped at about 300 lines and 12 capabilities, and code refuses a bigger one.
  • Tasks are planned just in time by a node planner when a piece starts.
  • An architecture pass opens every plan at the module level: which module owns which kind of work, one contract between each pair. Its rules become tests that run on every merge.
  • A re-plan fires when a piece passes its budget (twice the estimate) or goes two rounds with no new check passing.
  • A redraw of the plan fires only on a supervisor ruling, after a time or cost alarm.
  • The supervisor re-checks the plan every 8 active hours and before every release.
  • What passes down: a parent’s plan gives each child its goal, checks, budget and frame slice, frozen at the child’s start.

Context windows

  • Every step is a fresh session with one job, ended when the job is handed back. Nothing carries over except what is on disk.
  • Each brief has a size limit set from what each role measured at start in v0.4, plus a pack budget. A builder starts at about 29k tokens and the supervisor at about 33k. A normal fresh Claude Code session (started with go), about 63k tokens, is the ceiling for judgment roles.
  • Code refuses a brief over its limit and checks the count on the session’s first turn.
  • A session that grows too large is replaced. Past 150k tokens of context is a notice; past 250k, code stops sending it work and starts a fresh one at its next hand-back. A flat builder may reach 500k and hands over once.
  • A session that spends without landing is stopped. 3M weighted tokens since its last landed work stops it at its next hand-back; 6M stops it outright.
  • The CEO pane is rotated with the live conversation carried over, never mid-exchange.
  • A session never sees past transcripts, other pieces’ working notes, or the builders’ routine chatter.

7. Error handling: a ladder, one step at a time

  1. A check fails. Its builder fixes it.
  2. A piece stays stuck past its budget or for two rounds. Code launches a node planner to re-plan that piece.
  3. The same problem shows up in many places (three places in two pieces). Code moves the fix to the piece that owns that kind of problem, so it is fixed once at the root.
  4. Time or money runs on without progress, or no piece owns the problem. The watchdog wakes the supervisor, and its ruling binds. It can re-plan, redraw the plan, loosen a dependency between pieces, move named cases to the next version (at most a tenth of a version’s cases), or ask you for one short working session.
  5. The goal itself looks wrong. In your runs, you rule. Otherwise the supervisor rules with a default you can reverse at your daily review.
  • A piece that fails again after two redraws in one version is paused, the rest carries on, and you are told.
  • A builder can say “this test is wrong” mid-build, once per test per version, and the supervisor rules.
  • A builder can ask a question without it counting as a failure.

8. Monitoring

  • What is watched: time, money and progress on every piece, plus how much of the run goes to coordination instead of building.
  • A count of failures only triggers a local fix or a re-plan of one piece, because on last week’s logs count alarms also fired on healthy runs.
  • Time or money spent without progress wakes the supervisor once (then a cool-down), and its ruling binds; these alarms fired on no healthy run.

The watchdog checks every 30 minutes, and some signals every active hour.

Signal What it means Wakes the supervisor at
Spend a piece costs far more than planned twice its budget (4 times its estimate)
Tokens per finished piece work keeps costing without finishing 2.25 times the run’s average
Waiting a piece is stuck behind another blocked more than 2 hours
Cost per passing case one part is far costlier than the rest 3.1 times the run’s median (2.5 is a notice)
Flip-flopping fixes keep breaking what worked cases flip from pass to fail more than 6 times in a version
Slow progress failures are cleared too slowly still slow after a cool-down

Efficiency watch:

  • Coordination share (planning talk, reviews, retries) is a notice over 30% and a cost review over 40% twice.
  • Planning targets 15% of the run’s usage, with a 20% ceiling.
  • Waste inside building is watched too: the context limits above, re-checks of passed work, full rebuilds where a targeted one would do.
  • Measured need: one Deckwright session spent 188.6M weighted tokens, an estimated 31% to 40% of it avoidable, mostly from long-lived workers re-reading a growing conversation.

On the board: cost and waste per finished piece, landings per hour, and how long a finished piece waits to merge.

9. Improvement between runs

  • The harness is frozen for the length of a run.
  • Every confirmed harness fault becomes a regression test before the next version.
  • One change ships per version, and a bad one is rolled back by pinning the previous version.
  • From level 2, the improver proposes one change at a time with a prediction, and a frozen replay of past runs judges it.
  • Its guards: it must not cause a new alarm on any healthy run, it keeps a safety margin above the highest value seen on a healthy run, it is scored on runs it did not read, and the judge owns nothing it could tune.
  • Who merges: Rowan merges defect fixes; changes to “done”, thresholds or the judge need your ruling.
  • It stays in shadow because a dry run confirmed its predictions only on data it had already read. It needs about 8 failing and 14 healthy runs before its verdicts mean anything, about 5 to 10 weeks at the recent pace. Until then it merges nothing.

10. Other big topics

The frozen checklist is “done”.

  • Each case is data: an input and an expected answer, with its source recorded.
  • Version 1 holds at most 300 cases; each next version adds at most 10%.
  • A case closes only if it failed before and passes after.
  • Coverage of an outside format (every construct it contains) is counted separately from the sampled cases.

The independent supervisor.

  • A fresh session that rules as you would, from the frame, your past rulings and evidence built by code.
  • It never builds, so it never judges its own progress.
  • One session sorts the try-out’s list, answers the release checklist and approves; only its approval releases.

The merge train.

  • Several finished pieces are checked at once and land one after another in seconds.
  • Each landing’s check has a budget of about 4 minutes at the 95th percentile, on 4 parallel check slots, and a cap of 5 minutes; going over is itself a failing architecture test.
  • Simulation says speed is set by how many AI sessions the usage limit allows, not by merging.

One builder plus one reviewer by default.

  • In a test, one session rebuilt a finished v0.4 goal alone in about 13 minutes against v0.4’s 2.2 hours, on about an eighth of the tokens, and passed every check.
  • It had a head start and graded itself, and it is only one sample, so level 1 runs one goal both ways.
  • It splits from the start only for several large independent parts, more than one outside data source to count, or money and other irreversible actions that need their own owner.

11. Decisions for Jaime

Already settled by you: the two-layer architecture and the rename to “harness process”; the six rules that keep branches from overlapping; Opus builders at level 1; pack budgets measured against a normal fresh session (about 63k tokens); coordination share measured by usage weight; Rowan decides goal-level redraws in runs with no end (such as the business goal), with your daily review; speed as a core metric.

Five decisions (pending).

  1. Is the piece (node) the right building block? Recommend yes; it stacks from a task to a business.
  2. Strategy up front, tasks just in time? Recommend yes; it holds direction without over-planning tasks.
  3. Separation of powers (CEO proposes, supervisor rules, code enforces, you sign the goal)? Recommend yes; a CEO pane judging its own progress caused the worst hours in v0.4.
  4. Role and domain packs for every session, assembled in code? Recommend yes, starting with five packs frozen across level 1.
  5. The proving path: replay, three bounded runs, a product, then one shop? Recommend yes; never the business first.

Six open questions from testing (pending).

  1. One builder plus one fresh reviewer by default, splitting only when it outgrows that? Recommend yes, with one level-1 goal run both ways.
  2. Does a new kind of problem on the product’s hard part (its core capability, named at the start) hold the release? Recommend yes; elsewhere it goes to the next version.
  3. When you are away for 2 hours, may the supervisor sign the goal with a default you can reverse? It also covers a stuck top-level piece (continue the untouched parts, or pause). Recommend yes for bounded runs, never for an expansion or a goal change.
  4. Does your typed cut or stop take effect at once, even during an alarm? Recommend yes.
  5. May the supervisor ask you for one short working session on named cases? Recommend yes, at most once per run per day; unanswered, the cases just wait.
  6. Does the improver stay in shadow until about 8 failing and 14 healthy runs exist? Recommend yes.

Five review findings (pending).

  1. May the away-default (the supervisor’s sign-off when you do not answer for 2 hours) also settle the big policy calls? Recommend no: they wait for you, only the work that depends on them waits, and fold this into question 3.
  2. A lean flat path? Today “one builder plus one reviewer” still runs about eight sessions. Recommend one planning session, one check, your sign-off, one builder, one reviewer who also tries the product, one approval.
  3. Split the first proving step? As written, all 30 mechanisms are built before the flat comparison runs. Recommend building the lean flat path first, then the splitting machinery only if the comparison needs it.
  4. Pre-flight tests (tests run on the harness before any real run) for draft 10’s new mechanisms? Recommend yes: about five more, for cool-downs, the 2-hour away rule, the caps on moving cases and on meetings, the start-of-run rules, and the time and cost alarms.
  5. Check hard-part problems that join a version like any other case? Recommend yes: a source and a supervisor check for each, and more than a tenth of the version’s cases counts as scope overflow; decide it with question 2.

Test results and open risks

  • The core held: seven tests tried to break the design and none broke the piece, the frozen checklist, the uncapped try-out, the independent supervisor or code owning every step.
  • Earlier detection: time and cost alarms caught 4 of 5 failing runs at 3.0 to 6.3 active hours and fired on no healthy run; the 3-hour target is not met, and one failing run is missed by everything.
  • Waystar: the supervisor would have ruled at about 5 to 6 working hours instead of hour 63.
  • Prompt tests: 98 of 116 checks passed (84%), but only 11 of 22 case runs passed every check.
  • Unproven: alarm settings come from one week of runs; cost figures are a model; about half the simulated speed-up rests on assumed rates; the flat result is one sample; business scale has not been tested.
