How every instantiation of Rowan loads context

Version 0.3.1Updated 2026-11-28

The “today” claims, mechanisms (M1 to M10c), use cases (a to h) and gaps (1 to 6) are in my-lib/runtime/.tmp/261128-context-design/FACTS.md. Binding rulings: memory feedback_instantiation-levels-and-sliced-identity and Jaime’s decisions of 2026-11-28 (three axes, domain folders, memory and context files, indexes first, no packs, a write-time tag check). Built on: runtime/deliverables/261126-project-foundation-plan.md and the orchestration rules in skills/long-run/references/research/261126-orchestration-design-rules.md.

Terms:

  • Instantiation: one running copy of Rowan, from a terminal pane to a subagent.
  • Universal context: what every instantiation on Jaime’s machine loads, whatever it is doing.
  • Instance context: what one instantiation loads because of its level, place, function, expertise or domains.
  • Level: L1 (everpresent pane and the nightly dream wake), L2 (work threads, raw Rowan or a persona), L3 (subagents and long-run workers).
  • Function: the job in the work loop: plan, build, review, decide, audit, or generic.
  • Expertise: who is needed for the work (a branding expert, a marketer, a software developer, a CFO), held as persona skills and expert skills.
  • Domain: what the work is about (billing, Magic: The Gathering, mahjong, branding and so on). Each domain is a folder of context files.
  • Memory: dated experience with its reason, written automatically as work happens.
  • Context file: curated, authoritative knowledge, kept in a domain folder or a project’s context/.
  • Slice: the part of a larger source (identity, memory, a domain’s index) chosen for one instantiation.
  • Assembler: the one script that builds instance context. It is code; it makes no judgment.
  • Auto-memory: Claude Code’s own memory feature, which loads ~/.claude/projects/<cwd-slug>/memory/MEMORY.md.
  • Unprobed: a Claude Code behaviour seen only as a name in the 2.1.332 binary’s strings, never run. Step 1 of the build probes each one.

What every instantiation loads

Every copy of Rowan loads the same universal context, then an instance slice chosen by its level, the place it works and three axes: its function, its expertise and its domains. The universal part is the shared core, the personal layer, the workspace root rules and the identity core slice (who Rowan is, in about 600 characters). The instance part is everything else: more of the identity, a slice of memory, the project lens and project memory, the indexes of the relevant domain folders, the function directive, the named expertise, and the brief.

At start an instantiation loads indexes, never whole libraries. A domain with 40 context files costs 40 one-line index rows; the model opens a file when the work needs it. One assembler builds the instance part for every level from frontmatter, so a new domain file or a new memory reaches the right instantiations by its tags.

Rowan’s full memory index stays in Rowan’s homes. Projects turn auto-memory off, so a project session gets its own memory through its CLAUDE.md import and a Rowan slice chosen by the project’s domains. L1 gets the widest slice and a view over every other level: it reads the record the assembler writes of what each instantiation loaded, and the nightly dream wake governs the lessons that flow up.

  • Identity: every level gets a slice, where today it is on or off.
  • Memory: Rowan’s homes keep the full index, and projects get a slice by domain, where today the full index loads everywhere.
  • Function, expertise and domain: every L3 gets them, where today “role” and “domain” are a long-run harness (lr5) feature.
  • Curated knowledge: domain indexes put the right rows in front of the right instantiation, where today central context is read by chance.

Three axes choose the instance context

The single word “role” used to carry two meanings: the job a subagent does and the expert it stands in for. The design splits it, and adds the subject the work is about.

Axis Question it answers Size Curated knowledge (context) Experience (memory) Vocabulary owner
Function Which job in the work loop? Six, fixed Function directives and skills Memories tagged functions: team-lib/config/functions.yaml
Expertise Who is needed? Grows with need Persona skills and expert skills The skill’s own references None: find-skill searches the skills
Domain What is the work about? Nearly unlimited Domain folders and project context/ Memories tagged domains: The folders themselves

Functions are a small fixed list

team-lib/config/functions.yaml holds six functions, each with a one-line meaning and the directive that carries its working rules:

  • plan: break work into steps and choose the order.
  • build: make or change the thing.
  • review: check work against its spec and evidence (this covers “check” and “review”).
  • decide: choose between options and record why.
  • audit: check a system against its rules after the fact.
  • generic: none of the above; the default when a brief names no function.

The nine lr5 role packs map onto these: builder and pipeline builder to build, planner and node planner to plan, decider to decide, gate reviewer and reviewer-walker to review, auditor to audit, generic to generic. Each function’s shared rules move into one directive, team-lib/directives/function-<name>.md; the lr5-only variants (node planner, pipeline builder, gate reviewer, reviewer-walker) stay in lr5 as skill references. Each holds only its lr5-specific additions and links its function directive, so a function’s rules live in one place. Adding a function is a change to the shared core’s vocabulary, so it is a proposal Jaime approves.

Expertise is found as skills

Expertise has no vocabulary file. A persona skill (for example rc-cfo) or an expert skill carries it, find-skill finds it, and build-expert-pipeline creates a new one when none fits. A brief names expertise by skill name; the assembler adds that skill’s summary row and path, and the subagent loads the skill when it starts work.

Domains hold the most knowledge to curate

Function and expertise say how to work; the domain holds what is true about the subject, so it gets the most structure: a folder per domain.

A domain is a folder of context files with a generated index

Each domain is a folder holding many context files and one generated index.md, a one-line summary per file built by build_index.py from each file’s summary:. A memory’s domains: tag names a folder that exists.

Where domain folders sit

Knowledge Folder Example
One project only projects/<p>/context/domains/<domain>/ echo1/ in the Echo1 project, mahjong/ in mahjong-card-db
Two or more projects, shared with teammates team-lib/context/domains/<domain>/ billing/, brand-design/, third-party-data/
Two or more projects, Jaime’s own my-lib/context/domains/<domain>/ mtg/ (Deckwright, card valuation, the mana base builder)

A project’s domains live with the project, so its git history and its worktrees carry them. The shared library (context/domains/ in team-lib or my-lib) holds only domains that two or more projects use. Both library folders are new directories beside the existing context/indexed/, registered in config/registry-map.yaml so the index builder and the census cover them. A file in context/indexed/ that belongs to one subject moves into that domain’s folder; context/indexed/ keeps what spans subjects (the workspace reference, the execution standard).

Each domain name lives in exactly one place: one project, or one of the two libraries. A domains: tag resolves against the project’s own domains first, then the shared library.

The first six domains are the ones in use today. billing and third-party-data (from lr5’s lens table), brand-design (from the memory tags) and mtg go in the shared library. echo1 becomes a domain of the project that holds Echo1 work (ridecare-main or the echo1 repo), and mahjong a domain of mahjong-card-db. The tag values secrets and cost get folders only if the dream wake proposes them; evaluation describes a job, so its memories retag to the review function.

Creating, merging and checking domains

  • Creating a domain is a deliberate act: make the folder, write at least one context file, and generate its index. A tag cannot create a domain.
  • A domain is born in its project and graduates by a move. When a second project needs a project’s domain, the dream wake or the audit proposes the move and Jaime approves. Code moves the folder into the library, rewrites every reference to it, and leaves a pointer in the project (principle 15: one implementation per capability).
  • Synonyms merge by folder. The dream wake proposes a merge (“brand” and “brand-design” hold the same subject), Jaime approves, and code moves the files into one folder and retags every memory and lens that named the other.
  • The audit flags a domains: tag that names no folder, a domain name that exists in more than one place (two libraries, or a project and a library), and a domain folder whose index.md is older than one of its files.

Memory holds experience and context files hold knowledge

The two stores do different jobs, and functions and domains each have both.

A lesson enters as memory. When it proves to hold, the tooling proposes promoting it and Jaime approves. Promotion has five destinations:

The lesson is It moves to
How to work (a method, a check, a step) A skill or a directive

The Rowan lens is the memory model’s existing path from a topic memory to a situational lens (T2 to T3 in project_memory-architecture-layers.md). That model has no tier for domain context files yet; build step 3 adds them and the five destinations to it.

The promoted memory stays, marked superseded with a pointer to its new home, so its Why remains on record.

Indexes load at start and files open on demand

An instantiation’s start-up load is a set of indexes and a few short bodies; everything else is one read away.

At start On demand
Universal context and the identity slice The rest of identity, at L1 only
index.md of each relevant domain folder, and of the project’s context/ Any context file the index lists
Rowan memory rows tagged with the instance’s functions and domains, plus importance 8 and above The full body of any memory row
The project’s full memory index, in a project (through the project CLAUDE.md import) The full body of any project memory
The function directive’s body Other directives and skills, through find-skill
The named expertise skill’s summary row The skill itself, loaded when work starts

The full text of a context file or memory loads at start only when its frontmatter says load: full, which is for a short file every instance of that domain or function needs (billing’s data meanings, for example). The assembly record reports each instance’s start-up size, so a domain whose index grows large is visible.

One assembler builds every instance from indexed files

The assembler is a single script, team-lib/executions/assemble_context.py (name proposed), with three thin callers. It takes a level, a working directory, a function, an expertise and a list of domains, returns one text block and writes one record. The spawning thread chooses the function, expertise and domains for a subagent, and the dream wake judges which tags a file deserves.

  • SessionStart hook (L1 and L2). It reads the level from PVRAGON_ROWAN_LEVEL and passes the cwd. Launchers set the level: the everpresent launcher and the dream cron set 1, an interactive session defaults to 2, a headless claude -p defaults to 3 unless its launcher says otherwise. It takes over from identity_by_role.py in the same build step that wires it, so no session runs without identity in between.
  • SubagentStart hook (L3 Agent-tool subagents). Agent-tool subagents get no SessionStart. The hook reads the subagent type from its input, runs the assembler, and returns the block as additionalContext, so the subagent’s prompt is never rewritten. The hook is unprobed (29 matches in the binary’s strings). Fallback: the parent runs the assembler itself and pastes the block into the brief it writes.
  • lr5 briefs.py (L3 long-run workers). Its role-pack, memory and domain slots call the assembler instead of their own loaders. lr5 keeps its node and code-map slots, which are run state.

The record is one file per day, ~/.local/state/rowan-context/assemblies/YYMMDD.jsonl, with one line per assembly: time, session and agent id, level, function, expertise, domains, every file included, its size and its hash. The audit deletes files older than the retention window (30 days proposed) and reports assemblies that grow. The 200-token lens cap and lr5’s 1,500 to 6,500-token memory cap become signals of the same kind. The record is what lets L1 see other levels, and what the audit checks.

L1 loads everything and sees every other level

L1 gets the full universal context, the full identity, Rowan’s full memory index, and the state files that today are only “advised”: current-state.md, the latest short-term facts and residue, and the latest dream-journal entries. The assembler pushes those at L1 instead of relying on the persona’s step 1. On demand, L1 reads what no other level reads: the assembly record, the session roster, the audit findings, every project’s memory index and every domain index.

The everpresent pane

The pane’s working folder is unverified (FACTS use case c is marked inferred). If it is my-lib/, the pane gets the full my-lib/AGENTS.md, which contains the shared core; step 1 of the build reads the launcher to settle it. Either way the folder is one of Rowan’s homes, so auto-memory stays on and loads the full index. The persona still loads by its skill, and the assembler pushes the state files the persona used to fetch by hand.

The dream wake

Today the dream wake loads no core at all (FACTS gap 3), because agents/ is outside both projects/ and my-lib/. The fix reuses the 11/26 mechanism: agents/CLAUDE.md becomes a symlink to the shared core, as projects/CLAUDE.md is.

L2 loads Rowan’s thread context plus the place it works

An L2 thread gets the universal context, the L2 identity slice (identity, signatures, defaults and the output style), and then what its place adds. Place decides the memory pool: Rowan’s homes (my-lib, team-lib, personal, agents, the workspace root) keep auto-memory on and load Rowan’s full index; a project turns auto-memory off and loads its own memory, its domain indexes and a Rowan slice for those domains.

A raw thread in my-lib

This is today’s use case a, with one change: identity arrives as the L2 slice instead of the whole file.

A thread in a project or a worktree

  • The project’s domains come from a new domains: field in its lens frontmatter, naming domain folders (deckwright: mtg; ridecare-main: billing, echo1). Each name resolves to the project’s own context/domains/ first, then the shared library. The assembler loads those folders’ indexes and the project’s own context/index.md.
  • A worktree loads the same, from its own branch: the lens, memory, context/ and .claude/settings.json are tracked files (11/26 plan), and the assembler reads them through git rev-parse --show-toplevel.
  • Adopt mode retires stale core copies, which ends the double load in old worktrees. It moves no worktrees: the 212 deckwright worktrees under my-lib/runtime/ keep loading the full my-lib/AGENTS.md, and the audit only flags them. Step 1 of the build confirms what adopt mode does to a worktree before the design counts on it.

A persona thread loads its skill on top of the place

A persona thread is an L2 thread for its place, plus the persona skill it loads. A persona is expertise at L2. In v1 nothing else changes: the persona keeps its skill_categories: for find-skill, and the assembler does not rerun when a persona loads, because that would need a fourth caller with no hook to fire it.

L3 is assembled from its function, expertise and domains

A subagent gets the universal context, a short identity slice, its function directive, its expertise row, the indexes of its domains, a slice of Rowan’s memory for that function and those domains, the project lens and the project’s full memory index when it works in a project, and the brief the parent wrote. The project index arrives whole because the project CLAUDE.md imports it, and it is small.

How each part is chosen:

  • Function. The subagent type from the hook input when it names a function in functions.yaml; otherwise a Function: line at the top of the brief, if the hook input carries the prompt (part of the step-1 probe). No function means generic, and the record says so.
  • Expertise. An Expertise: line naming a skill. The assembler adds its summary row and path; a name that matches no skill is recorded, and the subagent runs find-skill.
  • Domains. A Domain: line in the brief naming domain folders; if absent, the project’s domains: from its lens; if neither, none. A name with no folder is recorded as a finding and skipped.
  • Identity. The core slice for every function. Functions that judge (plan, decide, review, audit) also get the “Who I am” section, which tells them how Rowan decides. A subagent whose expertise sends messages gets the signatures.
  • Memory. Rows from Rowan’s memory whose functions: and domains: match, plus importance 8 and above, ordered by the existing rank score. Rows carry summaries and paths; a full body loads only for load: full. In a project the subagent also gets the project’s full memory index, through the project CLAUDE.md import.
  • Lessons. The subagent hands lessons back in its final report, as the core already says. It never writes memory.

Agent-tool subagents inherit their parent’s auto-memory

An Agent-tool subagent loads the same auto-memory as its parent (FACTS use case d; observed in a subagent started in my-lib, which had the full index). In a project the parent’s auto-memory is off, so its subagents get none. In Rowan’s homes the subagent gets Rowan’s full index on top of its assembled slice, and the design does not remove it: there is no per-subagent switch. The audit’s “no L3 got the full index” check therefore applies to lr5 workers only. Their launcher sets CLAUDE_CODE_DISABLE_AUTO_MEMORY (unprobed), so they get the curated memory slot alone.

lr5 workers are L3 by the same path: briefs.py calls the assembler with the node’s function (mapped from its lr5 role) and the workspace’s domains, and keeps its run-state slots (node, code map, ledger digest). That replaces memory_candidates() and the packs folder lookup, so lr5 and Agent-tool subagents share one implementation.

Identity reaches every level as a slice chosen by level and function

identity.md stays the single owner of identity. A new slices: map in its frontmatter names, per section heading, the levels and functions that receive it. Sections of the output style are referenced the same way. The assembler reads the map and copies those sections verbatim. Its self-check fails when a heading in the map matches no section, so a renamed heading stops the build instead of silently dropping that part of identity.

Memory is sliced by location first, then by function and domain

Location picks the pool: a file in a project’s memory/ belongs to that project, and a file in Rowan’s memory/ is cross-project. No scope tag is added. Within a pool, level, function and domain pick the rows.

Projects turn auto-memory off

Today link.sh points all 5,961 ~/.claude/projects/*/memory folders at Rowan’s memory, so the 22,926-character MEMORY.md loads in every project, worktree, subagent and lr5 worker, and an lr5 builder gets both its curated slot and the whole index (FACTS gap 2). The change:

  1. Every personal project sets autoMemoryEnabled: false in its tracked .claude/settings.json. new-project writes it for new projects and adopt mode writes it for existing ones, so worktrees carry it through git. The three team repos get it in their untracked .claude/settings.local.json, where audit_infra.py already writes claudeMdExcludes, so teammates’ sessions are untouched.
  2. L3 launchers (lr5 and other headless children) set CLAUDE_CODE_DISABLE_AUTO_MEMORY, which covers workers whose settings sources exclude the project file.
  3. link.sh links Rowan’s memory only for slugs whose path is one of Rowan’s homes: the workspace root, my-lib/, team-lib/, personal/ and agents/, with their subfolders. There is no shared folder for other slugs.
  4. Project memory keeps arriving the way the 11/26 build made it arrive: the project CLAUDE.md imports memory/MEMORY.md. That works in worktrees (the branch’s copy), and on a teammate’s machine.
  5. Rowan’s cross-project lessons reach project work as the assembler’s Rowan slice, chosen by the project’s domains.

Both switches are unprobed. Step 1 tests each one; the fallback for both is an unlinked slug, which step 1 also probes (row 8 of the probe table).

The write hook checks tags when a memory is created

functions: and domains: are required on memory files created after the cutover, and allow_memory_writes, the hook that approves memory writes today, checks them at write time:

  • What it checks. A Write that creates a memory file in Rowan’s memory/ or a project’s memory/ must carry summary:, functions: and domains:. Each function must be in functions.yaml; each domain must name an existing folder. [any] is an explicit value for a lesson that holds everywhere.
  • What it does on a miss. It denies the write with a reason naming the missing or unknown field, so the writing session fixes the frontmatter and writes again. An edit to an existing file passes, so older files stay editable.
  • Who fills the tags. session-debrief writes both fields when it writes a lesson.
  • What it cannot see. A memory file written by a script through Bash never passes the Write hook. The audit is the backstop: its “no new memory lacks tags” check reads the files on disk, so it covers those writes too.

The 33 files tagged roles: migrate by code: the field is renamed functions: and each value maps (planner to plan, builder to build, decider to decide, reviewer_walker to review, auditor to audit). The 1,284 older untagged files are not back-filled in one pass. An untagged file reaches L3 and project sessions only through the importance-8-and-above floor, and the dream wake tags an older file when it reads it for consolidation, recording the pass in its journal.

Lessons flow up and L1 governs them

Each level writes lessons to one place, and every move to a more shared place is a proposal Jaime approves.

  • L3 never writes memory. It hands lessons back in its report, so each memory folder keeps one writer.
  • L2 writes project lessons to the project’s memory/ and cross-project ones to Rowan’s, by the core’s rule. session-debrief writes the tags, and the write hook checks them.
  • L1 everpresent writes Rowan’s memory, and may correct another session’s context as deterministic repair (a stale link, a tag value that names a renamed folder) under the everpresent-governs ruling.
  • The dream wake consolidates both pools, tags the older files it reads, proposes domain merges, triages audit findings, and drafts promotion proposals to the five destinations.
  • The audit (audit-infra, built 11/26-27) gains checks over the assembly record: each level loaded what the design says, no lr5 worker got Rowan’s full index, no project session got another project’s memory, no new memory lacks tags (including files written through Bash), no domain name exists in two places, no tag names a missing domain folder, no domain index is stale, and no assembly failed silently. It also flags a project with sessions but no lessons, and prunes old record files. The canary project carries one broken case for each check, including an untagged new memory and a project with sessions but no lessons.

  2. Rowan’s whole index loads everywhere via 5,961 links; project lessons near empty. Closed by: auto-memory off in projects and lr5 workers; link.sh limited to Rowan’s homes; Rowan slice by domain; the audit flags projects with sessions but no lessons.   3. Core delivery depends on cwd; dream wake has none; worktrees double-load or get my-lib. Closed by: agents/CLAUDE.md link; adopt mode retires stale core copies; the audit flags worktrees under my-lib, which stay open.
