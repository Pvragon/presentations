1. One page

What changes. A v0.4 run is a flat queue under a CEO who judges its own convergence. v0.5 uses one primitive at every level, the node: a frame slice, finite exit tests, a budget and one procedure (Test-Recognise-Split-Commit, TRSC), done when its tests pass. Nodes form a persistent tree per product. Levels 1 to 4 of the owner’s ladder form the frame, written breadth-first and capped; level-5 tasks are decomposed as work meets reality. Done for release N is coverage-matrix version N, its expected results from an external oracle; one walk runs before acceptance, and only the decider’s accept releases. A bounded goal is flat by default (one builder plus one fresh reviewer over a frozen intake, matrix and checker) and decomposes only when it measurably outgrows one builder (s2.6). A code governor sends counts to local fixes and persistence in time or cost to an independent decider whose verdict binds (s5.1). Code assembles each session’s role and domain packs. Landings verify in parallel in a merge train: execution speed is a core metric (the owner). Coordination is capped at 20-40% and watched by G6; build-side waste by efficiency signals (s5.8).

Why. On the eleven v0.4 runs of 10-30 to 11-06, second-pass rework took most of the spend (261106-lr04-week-watch/SYNTHESIS.md s2): strength spent 87% of component tokens on 112 reopens; finish built 15 subprojects in 5.3 h, then reworked for 34 h; no pass managed the architecture (CO-01). waystar-sot-finish then spent 62 h on one acceptance item without producing its deliverable (PENDING 5, the third run of that shape).

What it fixes. All 114 inventoried failures map to a mechanism or to “not addressed” (s13). On v0.4 logs, draft 10’s time and cost signals fire on no healthy run and catch 4 of 5 failing runs at 2.97 to 5.84 active hours (decomposed runs; the flat path’s time is measured at level 1), measured per node under draft 10’s cooldowns and repeat bounds (falsification/08-draft10-retest.md, s5.1); the 3-hour target is not met. On waystar’s worst item a binding verdict lands at about 5 to 6 active hours instead of hour 63 (T2, F2-29). On one bounded goal a single session matched v0.4’s result on about an eighth of its tokens and a tenth of its wall time (T7; s2.6). Coordination is an estimated 16% of a level-1 run, usage-weighted, against 33% to 55% measured on v0.4 (s5.7). s5.8 catches waste inside build, an estimated 31-40% of one measured session, which G6 missed.

1.1 Two layers: the process and the records

The owner (2026-11-09) split the design into two layers. The runtime layer is the harness process, declared as data in falsification/harness-process.yaml: every step with its actor (code, a Claude prompt, or a person), every transition with its trigger and token bucket, every loop with a counter and a bound, the escalation ladder, and the signals with thresholds and cooldowns: one small loop, run at every node. validate_harness_process.py checks in code that every cycle has a counted bound, no step reads an input some path never produces, nothing releases without the decider’s accept, every multi-exit step has an exit mode, and every decider and planner step holds a subtree lock. The process/method layer is the work itself as typed ontology records (Want, Capability, Component, Contract, Construct, Node, ExitTest and the rest; research-process-layer.md s4): a knowledge graph validated by code (falsification/ontology_check.py, rules in s2.5). The product tree recurses; the process does not. “Graph” means only the knowledge graph.

2.2 TRSC, one procedure at every level

From research-goal-decomposition.md (TOTE, Soar, ADaPT, ReCAP).

  1. Test. Run the exit tests; all pass is done. On first entry, freeze goal, why, tests and budget (strategic planning, which always runs).
  2. Recognise, in code. A node the plan marks as a leaf, and every red cell of a node that has an owner, goes straight to an owner with the cell and the frame slice, with no Claude call. Leaf kinds: an owner leaf, a flat leaf (s2.6) and a scripted-loop leaf (below).
  3. Split, only when no leaf is marked and the node has no owner. Repeated red on an owned node goes to rung 2 through the budget rule’s 2-cycle counter, never straight to split (DF-22). Children come from failing tests. Code checks the WBS 100% rule (the children cover all of the parent), one parent integration test, that each child names a frame capability, and that each child’s exit-test code lives in its own files or a producer’s frozen contract (FX-13). A node-planner split makes at most about 5 children; the root holds the frame’s capabilities (about 12), so a v0.4-sized plan becomes two levels instead of a refusal (FX-10: the 5-children limit would have refused 7 of 9 v0.4 plans, T1 F1-16). One split session writes every child’s spec (FX-12).
  4. Commit. An input is frozen only when its producer’s exit tests pass; Commit checks this in code before a consumer starts (F-35). Siblings with disjoint write-sets and frozen inputs fork and start together. When a child finishes and specified siblings remain, the node commits the next one whose inputs are now frozen, with no re-split (t_next_stub). Read literally, draft 9 ran every capability’s leaves in series: 117 h against 21 h in simulation (FX-11; T4, F4-04).

Scripted-loop leaf (FX-14; CO-11, CO-12, CO-24). When a node’s work is many similar items, a script owns the loop and makes one bounded model call per item, about $0.15 per part against $0.36 for batch agents (T2, F2-23). It is sized from a measured batch of 3 to 10. Its first test runs 10 items against the full gate set, reports skip reasons, per-call setup tokens and round time, and checks that rollback restores every file (CO-24). Workers get a step and context budget and a small extract, never whole shared files (CO-12).

Caps (proposed): frame about 300 lines; about 12 capabilities of about 15 lines; contracts as interface signatures. Intake refuses a frame over budget, in code (v0.3’s specs grew sixfold in a day).

2.4 Rules the node carries

  • Done is its own tests. Closed children under a failing parent test yield one new child per failing test. Integration is the parent’s exit test.
  • Fix path. Code routes a failing test to its node’s owner with the test and the frame slice: no spec rewrite, no routing session.
  • Budget rule, the single stuck trigger: spend past budget, or 2 cycles (fix wave plus matrix run) with no new test passing, triggers rung 2; spend past twice the budget (four times the estimate) is rung 4. It applies to decomposed nodes; a flat leaf’s rung 2 is s2.6’s outgrow tests alone (ponytail review 4). Estimates include spec time and real capacity (F-25), in the work’s own unit with a range, re-measured after the first batch of each approach (CO-13: no estimate in session -16 was within 2 times of what happened). The governor’s lines stay on the frozen first estimate: a re-measured estimate is recorded for the next plan and the reference class, and moves the budget only by a decider ruling, so a node over budget cannot reset its own alarm.
  • Bounds. A bound is the number of traversals allowed; the trip is taken on the next attempt. Every rung-2 transition lists the counters it resets; an unlisted counter never resets within its scope (FX-59; the harness-process.yaml header).
  • Planning rules, prompt text at level 1: real data first, with performance and subset-rerun tests (F-17, F-30); one owner per file; code on fixtures; FS, SS, FF or SF timing; never drop a node owning a matrix cell; a report is not an exit (F-96).

2.5 The work ontology

Three tests independently found that nothing marked a node as the user’s deliverable or an exit test as open-ended, and the decider had no verdict to defer cells (T3 F3-02, F3-03; T2 F2-04, F2-05; T5 DEC-7). Both waystar decider runs in T5, with the facts in the brief, kept the deliverable waiting on a verification of history, the shape that cost 62 h. No field existed for a rule to test (FX-01, FX-02), so the ontology records (s1.1) gain fields and ontology_check.py gains rules (I-01):

Rules (level 0 for the schema and checker; level 1 for R13, R14 and R3b at intake):

  • R13, open tests: an exit test with population: open needs a budget, a trend counter and a named interactive fallback, or intake refuses it. Rung 2 on a node with an open red test goes to the decider, never to split, since a re-cut only copies the open test into each child (FX-03).
  • R14, the deliverable first: a node producing a user_output capability may not need a node whose capability is verification; such checks run beside the deliverable (FX-02, PENDING 5: “never gate the deliverable on verifying history”). A capability is one or the other: a node whose capability is verification may not also be marked user_output, so a check can never be relabelled as the deliverable to pass R14 (09-prompt-tests-draft10.md).
  • R3b, census: for an external format the Construct set equals its source census, by count and hash, at intake. Census coverage is a counter exit test (every construct decided and read, driven to zero), separate from the sampled correctness cells, so the 300-cell cap applies to cells only (s4; FX-43). The census rule covers any finite option set a capability chooses from, such as channels, product types or payers (FX-23). With a census, R3 flags 413 of 444 Forge constructs unowned at R6 plan time; without it, 4 of 16 (T3 F3-01).
  • R3 and R4 count reads owners only, exempt abstract parents and counter tests, and pull a read finding up to the reads owner and a value finding to the consumes owner (FX-06).
  • R9 compares only siblings whose needs timing lets them run at once (it misfired on 18 of 45 firings, FX-04); R8’s static half moves to code defaults (it fired on every node of both plans, T3 F3-11); R10 compares spec-level rulings within the test they settle; R12 is reworded so it no longer contradicts R1 (FX-18).

Authoring takes about 100 to 120 plan-time records, 6k to 10k output tokens plus 10k to 30k reading per effort, against runs of 54M and 205M; scripts generate ledgers, censuses and rulings logs (T3 F3-15).

2.6 The flat default (pending Q-1)

Evidence (T7, one sample). On echo1-billing-exec (the CEO billing waterfall page), one Opus session with no subagents rebuilt the goal from the same inputs in 12 min 45 s of wall time, peak context 260k, against v0.4’s 2.2 h and 14.6M weighted tokens. It passed all 33 automated checks and all 17 rubric items, and came closer to the post-review numbers on the two lines where the pages differ (falsification/07-flat-baseline.md). The report’s 3.73M weighted tokens counts all 133 transcript lines; deduplicated by API message id, as the v0.4 meter counts, it is about 1.84M over 67 messages (recomputed for draft 10 with lr/launch.py’s weighted()). Both sides deduplicated, the gap is about 8x in tokens (1.84M against 14.6M, 7.9x) and 10x in wall time; the report’s 4x used the undeduplicated 3.73M. Caveats: it had a head start (a better-understood model, prior notes), it scored itself, and it is one sample. It lacked independence: its two decisions that moved $15,776 were never challenged (FX-108). The harness’s frozen inputs (intake, rubric, automated checker) earned their keep; the decomposition did not (FX-107).

The default. A bounded goal starts as a root with one marked flat leaf: one Opus builder session, plus one fresh reviewer (gate_reviewer.md in flat mode) that reviews blind first and re-derives the key figures. Intake still freezes the intake document, the rubric or matrix and the automated checker. A flat run needs no new mechanism: it is a root whose Recognise step finds a marked leaf, and the budget rule is the outgrow trigger. The code step decompose_check (after the matrix freezes) chooses the shape.

Decompose from the start if any holds (starting values, I-04): 1. Parallel work for hours: 2 or more capabilities with disjoint write-sets, each estimated over 2 active hours of build. Below that, slots buy nothing (T4, F4-02: wall time scales with leaves over slots). 2. More than one judgment’s worth of scope: more than one external system or dataset needs its own census, or a census exceeds the cell cap (Forge: 444 kinds, T2 F2-01). 3. Separated authority: irreversible outside actions or money writes, which need an owner apart from the builder.

A flat builder has outgrown one session when any holds (the governor’s t_gov_outgrown, rung 2): 4. Context: past 500k, about twice the flat session’s 260k peak; it hands over once through its progress file, and a second time is a split. 5. Spend without progress: past 2x its estimate while the checker’s pass count has not risen for 2 cycles (T1, F1-04). A flat session has no fix waves, so the daemon runs the frozen checker on the builder’s branch at each progress-file commit, or every 30 minutes, and logs the pass count as an event; a flat leaf’s cycle is the interval between two such runs (review R-10). Both halves must hold, and the test never fires in the builder’s first 2 active hours (proposed): a builder past 2x whose pass count still rises is not split, nor one that spends its first hour reading with no check passing. The general budget rule (s2.4) does not apply to a flat leaf, so this is its only spend trigger (ponytail review 4). 6. Throughput: checker work stays serial for more than about 3 active hours while the frame shows disjoint capabilities waiting, read from the same checker events.

E1 and E2 are retuned for the flat leaf (s5.8): E1’s stop moves to 500k, and E2 counts from the last rise in the checker’s pass count. Draft 9’s limits would have stopped the flat session on E1 (260k past 250k); on the deduplicated count (1.84M) E2’s 3M would not have fired, so FX-81 holds for E1 only. Level 1 runs one of its three goals both ways, flat plus reviewer and decomposed, as a control (s12).

Rate signals on a flat leaf. A flat run has one node, so E3 (cost per landed cell against the run median) and W5 (tokens per close against the run’s average) have nothing to compare, and G3 has no fix waves. The daemon’s checker events feed them instead: G3 reads newly passing checks per active hour, and E3 the cost per newly passing check against the estimate’s cost per cell; W5 stays blind on a flat leaf. s5.3’s detection times come from decomposed v0.4 runs, so the level-1 control reports the flat side’s own detection time (ponytail review 4).

3. The frame holds the whole

The frame holds the whole vision (ruling 1), because the CEO’s memory failed at it:

  1. Every brief carries the frame slice (M1).
  2. Every split is checked in code (M2): each child names a capability; each test names the capability or contract it verifies, so a frame change flags only the tests on what changed (F-82).
  3. Decider checklist mode (M4). Before every release, every 8 active hours (proposed) and in every reframe verdict, the decider answers a checklist that can fail: every capability serves the want; every red class has an owner; no contract changed outside a ruling; the frame is in budget. A failed item is a rung-4 trigger; at release it is answered in the accept session, so a failed item stops the release (s4; review R-02).
  4. Pull-up (M3; ruling 2). When red cells share a class key (Deckwright: the effect-class row) at 3 or more places in at least 2 nodes (G4), code moves the fix to the lowest node owning that class; no owner is a rung-4 trigger, and the decider adds the central process.

The architecture pass (M5; ruling 9). Every pass at levels 3 and 4 starts from the modules, one contract per pair, and where each kind of interpretation may happen; a product translating an external format inventories its whole construct set at intake. Because an instruction alone failed (CO-01), these are exit tests: each kind of interpretation is owned by one module; every census construct maps to an owning node. The check finds where the data is read, whatever the syntax: an AST rule lists every read of the raw card-text field and every parse call site, and each must route through the schema module, so text read with in, .split() or a dict keyed on fragments is caught as surely as a regex (close-out had ~130 regex sites on card text and 98 of 138 trigger modes unnamed). Every architecture test runs on every landing, in the merge train at zero tokens (PR3-4); they are greps and AST scans that take seconds, and their runtime counts against the verify budget. Nothing selects them by touched paths: under the ratchet, a violation that a landing’s selection missed would be charged to the next landing that selects the test (ponytail review 4). A measured run past the verify budget is a failing architecture exit test. In simulation, a 10-minute test run on every landing takes the design point (5 slots) from 21.0 h to 22.1 h, and a 20-slot run with one verify slot from 9.0 h to 40.7 h (FX-89; T4 F4-08). The gate reviewer adds LLM judgment only on level-3 and level-4 landings and on a flat leaf (s2.6). The census follows R3b (s2.5), and intake lists the assumptions done rests on.

Architecture tests ratchet. At intake the daemon records each test’s violation count as its baseline. A landing fails only if it raises a count above the baseline; the baseline drops as violations are removed and never rises; the owning architecture child, or the adapter child, exits only at zero. On Deckwright the card-text test starts at about 130: a neutral landing passes, one that adds a read fails, and the refactor child drives the count down. Without the ratchet nothing lands on day one (F-05).

Contracts without pinning. Contracts are signatures frozen as children’s exit tests (F-21), unversioned, since pinning means two live implementations (F-15). A producer lands with every consumer’s tests green or, for many consumers (the card schema has eight, F-11), behind a temporary adapter whose child exits only when “the old interface has zero callers”.

Sign-off. The owner signs frame levels 1-2 at launch and on expansion in the owner’s runs; the decider signs 3-4 against the register before spend (F-84). When the owner is away, after 2 wall-clock hours with no typed sign-off the decider signs levels 1-2 of a bounded run with a recorded default the owner can reverse at the daily review, never for an expansion or a want change (proposed, pending the owner: Q-3). That exclusion is structure, not trigger text: an expansion has its own size check and levels 3-4 sign-off (signoff_expansion_l34), an expansion run-state flag guards the launch sign-off, the default and the intake reframe, and the validator proves no path reaches either sign-off while the flag holds (T2 F2-14, falsification/08-draft10-retest.md s3). The timer is wall-clock because the active clock stops while the run waits for the owner, so an active-hour timer would never fire at night (review R-03). Whether the default may cover bulk policy decisions (s3.5) is review finding R-04 (s14). Without it, echo1’s 2.2 h run, started at night, would have waited until morning (FX-27; T2 F2-10). The owner’s approval of a plan signs levels 1-2; its needs edges are plan facts the decider may change (FX-77). In the ultra-long category the operator decides levels 1-2 reframes, with the owner reviewing daily (level 3).

3.1 Requests and expansion

A request, from the owner or the CEO, is a proposal (M10). One decider session classifies it and picks the re-entry node from code evidence: the capability ids it touches (M2), their lowest common ancestor, and whether it needs a new capability.

New scope cells under existing capabilities; may reframe levels 3-4 lowest common ancestor; its architecture tests re-run decider; 10% scope budget (s4)
Cut cells removed from N (a done change, logged in the release notes) the node owning the cells, which re-tests The owner’s typed turn binds at once, uncapped; a cut the CEO proposes is a deferral, under its 10% cap and hard-part guard (s5.5)

The task list is a view of the tree’s frontier, with no queue to append to (F-34). An expansion is rung 5: in the owner’s runs the CEO shows the level-1 and level-2 diff and the daemon records the owner’s typed reply before any spend; only the new scope waits. An expansion the owner typed is already signed and is not shown back (FX-35). In the ultra-long category the operator rules via the decider path.

The owner’s typed rulings bind at once (proposed, pending the owner: Q-4). A typed cut, stop, scope change or want change reaches decider_classify with the owner’s quote attached; the decider only picks the node, and no active governor signal holds it. It pre-empts the subtree lock, because picking a node is not a ruling, and duplicate matching never applies to the owner’s typed turns (review R-22). A binding session carries the subtree’s ruling version from its start; a verdict stamped before an owner’s ruling on that subtree is refused, and the decider relaunches once on the current state, so a verdict already in flight cannot overwrite the owner’s last word (ponytail review 4). Draft 9 refused such changes for lack of a decider classification, or held them behind a signal and reported back (FX-30, FX-31; T2 F2-17, F2-18). The hold stays for CEO-proposed expansions. 3.4 Branch ownership

Approved by the owner, 2026-11-08: “great, approved on your plan for 1-6”.

The owner (11-08) asked how branches avoid v1 and v2’s merge burden. Conflicts surfaced only at merge (F-65), builders wrote outside their files (F-66), shared files had split owners (F-16), and hot files drew the rework. Code prevents overlap on existing paths, with no new role:

  5. Shared interfaces change only through their owner, by pull-up or an architecture child with the temporary adapter; consumers never edit a shared contract.

  • Re-plan X counts against the node’s one re-plan; once that is spent, the verdict becomes a reframe, and the decider pack says so (review R-22).
  • Defer cells moves named cells to N+1 with a notice. Deferral is a done change made under time pressure, the shape of F-03 (“never redefine done to fit a deadline”), so code caps it (defer_cap_check; review R-01; proposed): cells deferred in one release, summed over every defer verdict, are at most 10% of N’s cells, and a third defer verdict in a release is a reframe. A deferral past the cap goes to the owner, never to more deferral. A hard-part cell is never deferred without the owner’s typed turn and stays in N meanwhile, and so is a cell named in an item waiting on the owner (a sitting, an outside input). A cut the CEO proposes is checked as a deferral; only the owner’s typed cut is uncapped. Deferred cells queue first in N+1 and count against this cap only, not N+1’s 10% scope budget, which measures new classes: counting them twice would turn the first new class after a full deferral into a reframe for the wrong cause (ponytail review 4, revising R-01’s part 2).
  • Interactive session (proposed, pending the owner: Q-5): the decider prepares a brief and asks the owner for one bounded sitting on named cells, with money where the product has it, while the rest of the tree continues; at most one request per run per day. An unanswered request defers nothing: the cells stay in N, that node waits, the rest of the tree continues, and the request is listed in the owner’s daily digest (review R-01). Both waystar’s and finish’s close-outs reached this fix by hand (“bridge the residue with the owner in one sitting”, PENDING 5).
  • A reframe names the work it removes or redraws (F-80); the daemon diffs the frame’s capability-to-module map and contract set before and after and refuses an id-only diff, so a relabel (finish’s C21, C22, C24 re-cut as SP1, SP2, SP5) cannot pass (F-14).
  • The verdict binds (M11): the daemon stops dispatching work it touches; running gates finish.
  • Holds run on the wall clock: verdict within 1 h, then the action the verdict names (a re-plan launch, a reframe, an expand) within 2 more (proposed; FX-76); past either, the daemon notifies the owner and relaunches a dead CEO.
  • Notifying the owner holds only its item; the rest of the tree continues, and the owner’s next typed turn re-enters as a normal turn. If the held item is the root, the decider records one default per release from a fixed list: continue the subtrees the held item does not touch, or pause. A done change, a want change or a hard-part acceptance always waits for the owner. The default is reversible at the owner’s daily review (DF-30, I-07; review R-08; proposed, pending the owner: Q-3).
