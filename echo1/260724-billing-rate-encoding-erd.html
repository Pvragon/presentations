Why a rate schedule is four tables, not one

Each seam below is a genuine one-to-many. A single flat table can hold the fixed core of a rate, but not the three varying-length lists hanging off it — that's the whole reason to normalize.

payer 1 ──< ∞ rate_schedule 1 ──< ∞ rate_component ＋ rate_add_on

01The flatten test

Put a payer's rate on one row and try to store two real contracts side by side. Griffin fills 3 fields; Larned needs 20+, several of them repeating. The flat table can only cope by guessing a column ceiling and drowning in NULLs — or by hiding the lists in a blob SQL can't see.

Breaks three ways. A 6th add-on = schema migration. ~90% NULL. "Which contracts have a fuel surcharge?" means OR-ing addon1..addon5. The blob alternative removes NULLs but is invisible to CHECK / FK / index / RLS / audit.

normalized each list element is a row
rate_schedule Larned · grain=vehicle_journey · base=tiered_per_mile · min=85

↳ rate_add_on fuel{gas>5}=0.50/mi
… +3 more add-on rows
rate_schedule Griffin · grain=frequency · monthly=6250 · 0 children

Bends, doesn't break. 5 add-ons = 5 rows, 0 = 0 rows, a 6th = one INSERT. Every element is queryable, constrainable, and individually audit-logged.

02The relationships

Only rate_schedule, rate_component, and rate_add_on are the encoding. The rest already exist — they're where a priced unit comes from (transport) and where it lands (invoice / invoice_line). The one net-new column on the operational side is transport.journey_id.

The load-bearing idea

Every table exists because there's a real one-to-many at that seam — payer→schedules, schedule→components, schedule→add-ons. Normalizing isn't extra structure; it's the only structure that lets a 6th add-on or a brand-new contract arrive as data (an INSERT) rather than a schema migration. That's what "encode any future variation" actually requires.
