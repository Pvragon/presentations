RideCare · Billing Rate Encoding — Revised Proposal, for Roman's review

payer → rate_schedule → rate_line, one billing chain for 837 and invoice

Rate encoding is three tables: rate_schedule (a priced regime) owns rate_line (each priced term) as a real one-to-many; payer points at the schedule new rides price against. Both 837 filing and contract billing run through one chain — billing_export_batch → claim → service_line → transport — split only by output_type on the batch.

payer N ──1 rate_schedule 1 ──< ∞ rate_line

Decided vs. open

  • Decided: rate_schedule + rate_line replace all four old rate tables; one billing chain serves both 837 and contract invoice via billing_export_batch.output_type; the old invoice tables are gone.
  • Open — needs Roman's call (§5): how service_line represents a vehicle_journey charge — new journey_id FK vs. a lead-transport hack.
  • Unchanged: the 837 path itself — filing logic and insurance claim shape are untouched by this proposal.

billing_export_batch → claim → service_line → transport

Unchanged from tier-2, with one addition: billing_export_batch.output_type (enum: edi_837 | invoice_csv), NOT NULL, stamped at generation — the batch is a historical record, so deriving it later from payer_type would silently mislabel past batches if a payer's type is later corrected. Contract-only fields (period_start, period_end, due_date, invoice_number, delivery fields) live on the batch, nullable for 837 batches. The old invoice and its per-line table are gone — folded into billing_export_batch and service_line. The 837 path is otherwise untouched.

03Versioning

  • A rate change is an INSERT of a new rate_schedule row (+ its rate_line rows) — never edit a schedule already billed against.
  • Same schedule_key, incremented version — a genuinely different schedule gets a new schedule_key.
  • payer.rate_schedule_id repoints to the new version; old rides are unaffected.
  • transport.rate_schedule_id is stamped at pricing time, never recomputed — that's what preserves history.

04Three billable grains

rate_schedule.billable_grain decides what the biller iterates — independent of the rate math.

grainunit billedscope
person_legone client A→B837 (X12 = 1 patient/claim) + per-person contracts
vehicle_journeyone vehicle trip, 1..N patients, ONE unit ("per trip, not per person")contract/invoice only
frequencyone payer × one period ($/month)contract only — lines all $0, fixed charge on the batch; transports still ride along as manifest + feed the cap

06Open question — for Roman

What does service_line point at for a vehicle_journey charge?

  • Option 1 (leaning): add service_line.journey_id, make transport_id nullable, CHECK (num_nonnulls(transport_id, journey_id) = 1) — a clean XOR. Requires promoting journey from a derived grouping key to a thin real table (id, tenant_id, route_id, cached measures) as a valid FK target. 837 lines always set transport_id and leave journey_id null — 837 is unaffected.
  • Option 2: charge rides on a "lead" transport, siblings billed $0, grouped by transport.journey_id. Zero change to service_line — but reproduces the V1 TANF $0-sibling hack, distorts per-patient analytics, and invents a "lead transport" concept with no contract basis.
  • Note: a vehicle_journey is derived from existing data by grouping transports on (route_id, pickup_facility_id, dropoff_facility_id) — every intake address resolves to a facility, including private residences.
