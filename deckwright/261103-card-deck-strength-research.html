Recommendation

Feature-based pod ratings (Deckwright C21 features + sim pieces, rating residual), components ratings, deck-stat, deckwright, decomp-sim. - Model: P(seat i wins) = softmax over the pod of (w · x_i + r_i). x_i is C21 feature counts (mana, draw, tutor, interaction, veto cost) plus SP4 pieces (on-curve, combo by turn 6, interaction by turn 4) [3][4][6]. r_i is a deck or commander rating with a strong L2 penalty, so it moves only when data supports it [2]. - Why: ratings alone are the best-validated method but cannot score an unplayed deck and need about 610 games per deck [1][2]. Shared feature weights fix both. Deterministic structure plus fitted weights beat hand weights in chess (Texel) [3]; Deckwright’s own scores then become features, not verdicts [3]. - Card strength: the marginal change in w · x when a card is added or cut. It is explainable through C21 [6]. - Not chosen now: plus-minus (data-hungry per card), Forge simulation (biased pilot, 264 games/h), RL (15-45 h per deck, no four-player evidence) [2][5][7].

Reliability

How we would know it works (docs/research/sp1-ground-truth/validation.md [1]): - Primary metric: log loss on pod winners, and skill = 1 - log_loss / ln(seats). Skill above 0 beats chance; ln 4 = 1.386 for four seats. Secondary: Brier and top-1 accuracy. - Hold-out split by time and by event, fixed before tuning. - Target: skill above 0.02 on about 300 held-out pods, and above plain ratings on decks unseen in training. - Deck-level claims: a 30% deck vs the 25% seat baseline needs 610 games (SP2, power 0.8) [2]. Separating two decks 5 points apart through agents needs 1,153 games per deck at four seats (SP5) [5]. So single-deck claims must pool by commander; the model is judged on game-level log loss. - Today’s confidence: medium-low. Every component works on synthetic data only; none is yet scored on real Commander pods [2][4]. Deckwright’s 0.881 pair agreement is with its authors, not outcomes [3].

  • Phase 2 data: EDHTop16 standings and Playgroup.gg commander win rates (about 47k games a month) as coarse cross-checks for casual tables [1].
  • Phase 3 data: a tracker partnership for casual per-game logs, if casual pods disagree with cEDH [1].
  • Compute for the recommendation: seconds per fit on a laptop; C21 lookups and SP4 pieces under 1 s per deck [4][6].
  • Engine compute, only for later phases: Forge measured 264 games per hour (264.5, 8 workers, four seats, 120 s clock) in docs/research/sp7-engines-ai/forge-speed.json [7]. That is about 3.8 h per 1,000 games and an upper bound.
  • RL, if ever: 15-45 h per deck on this host’s 20 threads; a general agent is 63 days on Forge [5].

Roadmap

  1. Validation set and baselines. Build the TopDeck.gg fetcher and decklist-to-card mapper (1-2 days) [1]. Score uniform, plain ratings and Deckwright-only predictions by log loss on a time-split hold-out [1][2]. Exit: 1,000 pods with full decklists loaded, drop rate reported, baseline skill numbers recorded.
  2. Feature-based pod ratings. Fit w on C21 features and SP4 pieces, residual r with cross-validated L2 [2][4][6]. Exit: hold-out skill at least 0.02 and better than plain ratings on unseen decks; weights have sane signs.
  3. Card attribution and Deckwright feed. Turn w into per-card marginal values; add pm-prior for staples with enough seats; compare with Deckwright’s current ranks [2][3]. Exit: card values agree with outcomes better than Deckwright alone on held-out decks, then hand to the Deckwright build run.
  4. Engine and RL features (optional). Only if a validated gap remains for high-skill or combo decks: add Forge sim win rates as a biased feature, then the SP5 per-deck agent route [5][7]. Exit: the added feature improves hold-out log loss by more than its noise across repeated splits.

SP1 Ground truth: outcome data inventory

Machine-readable list: sources.yaml (checked by tests/sp1/sp1_gt.py). Protocol: validation.md.

Question

Which public data records who actually won a game of Magic, at what grain and volume? A card or deck strength estimate (SP2-SP8) is only as trustworthy as the outcomes we can score it against. Popularity data such as EDHREC (https://edhrec.com) measures choice, not results, so it is listed but marked outcome: none.

Commander data

  • cEDH pods, game grain. The TopDeck.gg API returns each round’s tables with players, winner and status, plus decklists once public. It is free with a key and a visible credit (https://topdeck.gg/docs/tournaments-v2). This is the only public per-pod winner source found.
  • cEDH standings. EDHTop16 aggregates TopDeck.gg cEDH events into standings and win/loss/draw records per commander and pilot; all Command Tower events are added automatically (https://edhtop16.com/about).
  • Casual Commander. Playgroup.gg ranks 794 commanders by win rate from 46,776 tracked paper games in 30 days, normalised to a 4-seat baseline, with a 40-game, 10-pilot floor (https://playgroup.gg/commanders/tier-list). Only aggregates are public; raw game logs are not.
  • Arena Brawl. Untapped.gg shows Historic Brawl commander win rates over a rolling 3 months (https://mtga.untapped.gg/commanders). It is 1v1 Brawl, not 4-seat Commander.
  • Popularity only. EDHREC and the cEDH Decklist Database (https://cedh-decklist-database.com) have no outcomes.

Limited and constructed data

  • 17Lands publishes per-game CSVs per set and queue (deck, hand, mulligans, turns, won flag) under CC BY 4.0; the FDN PremierDraft game file is 60 MB gzipped (https://www.17lands.com/public_datasets). This is the richest public win/loss data in Magic, but it covers Arena Limited only.
  • Arena constructed. Untapped.gg gives deck and card win rates from tracker users, as aggregates only (https://mtga.untapped.gg). Wizards holds every Arena game but does not release logs (https://magic.wizards.com/en/mtgarena).
  • Tournaments. MTGO publishes Challenge standings and 5-0 league lists (https://www.mtgo.com/decklists); MTGTop8 archives top finishes across formats (https://www.mtgtop8.com). Both give placement, not games.

Gaps

  • No public per-game log for casual 4-seat Commander. Playgroup.gg holds logs but publishes only aggregates (https://playgroup.gg).
  • Turn order and game length are not among the TopDeck.gg table fields (table, players, winner, status) (https://topdeck.gg/docs/tournaments-v2).
  • Draws and intentional draws are common in cEDH Swiss rounds and carry no winner (general knowledge).
  • Pilot skill is confounded with deck strength in every tournament source (general knowledge).
  • Scraped sources (MTGO, MTGTop8, EDHREC) can change layout or terms without notice (general knowledge).

Verdict

A Commander validation set can draw today on cEDH pod winners with decklists from the TopDeck.gg API (https://topdeck.gg/docs/tournaments-v2), with EDHTop16 standings as a coarser cross-check. For casual Commander only commander-level win rates exist (Playgroup.gg, about 47k games a month), which can check a ranking but not score per-game predictions. Missing: public casual per-game logs, turn order, and any way to separate pilot skill from deck strength. 17Lands remains the best place to test methods on plentiful game-level data before moving them to Commander (https://www.17lands.com/public_datasets).

SP1 Validation protocol

Every method in SP2-SP8 reports results in this form. Reference code: tests/sp1/sp1_gt.py. Sources: sources.yaml and README.md.

Targets

An estimate is scored against one of three observed outcomes, from finest to coarsest: 1. Game winner: which seat won a pod or match. Commander: TopDeck.gg table winner (https://topdeck.gg/docs/tournaments-v2). Limited: 17Lands won (https://www.17lands.com/public_datasets). 2. Placement: final standing in an event (EDHTop16, https://edhtop16.com/about; MTGO, https://www.mtgo.com/decklists). 3. Deck win rate: a deck’s or commander’s share of wins against its seat baseline (Playgroup.gg, https://playgroup.gg/commanders/tier-list). Draws, intentional draws and unfinished games are dropped by the caller before scoring; report the drop rate next to every result (general knowledge).

Metrics

score_games(preds, winners) takes one dict per game (seat -> win probability) and the winner. - Primary: log_loss, mean of -ln p(winner), and skill = 1 - log_loss / baseline_log_loss. The baseline is the uniform guess, ln(seats), so 4-seat pods and 1v1 matches share one scale. Skill above 0 beats chance. - Secondary: brier (sum over seats of squared error) and accuracy (winner alone has the top p). Log loss is a strictly proper scoring rule, so honest probabilities score best (https://en.wikipedia.org/wiki/Scoring_rule). Card-level methods turn card scores into deck win probabilities first, then go through the same scorer.

Holdout

  • Split by time: fit on events before a cutoff date and score on later events, never at random. This keeps the metagame drift and ban-list changes the method will meet in use (general knowledge).
  • Keep every game of one event on the same side, so pilots and decklists do not leak across.
  • Report the cutoff, event count and game count. Fixing the holdout before tuning anything matters more than its exact size.

Sample size

min_games(p0, p1) gives the games one deck needs before its win rate p1 is told apart from the seat baseline p0 (two-sided z test, alpha 0.05). For a 4-seat pod, p0 = 0.25:

Validation set

Smallest set worth building: about 1,000 cEDH pods with a known winner and all four decklists, pulled from the TopDeck.gg API (https://topdeck.gg/docs/tournaments-v2), from at least 20 events, split by time into roughly 700 for fitting and 300 for holdout. Estimate: a skill gain of 0.02 is a log-loss change of about 0.028 on a baseline of ln 4 = 1.386; with a per-game paired SD near 0.3 that needs about 900 games (general knowledge). Add a 17Lands set (one set, PremierDraft) as a high-volume control (https://www.17lands.com/public_datasets). Placement-aware metrics (rank of each seat, not just the winner) are future work.

Cost

  • TopDeck.gg: free API key and a visible credit. 1,000 pods across 20 events is well under the 1,000,000 documents a day and 50 requests a minute on rounds endpoints (https://topdeck.gg/docs/tournaments-v2).
  • 17Lands: one gzipped CSV per set, about 60 MB, free under CC BY 4.0 (https://www.17lands.com/public_datasets).
  • Engineering: one fetcher and a decklist-to-card-ID mapper, about 1-2 days. No paid data is needed (general knowledge).
  • Casual Commander per-game data would need a partnership with a tracker such as Playgroup.gg (https://playgroup.gg).

Statistical strength methods for Commander

Four families can turn game records into strength estimates: ratings, card win rates, plus-minus (ridge regression on cards) and deck-stat regression. All four run in the spike docs/research/sp2-statistical/spike/sp2stats.py (stdlib Python) on 4-player pods where only the winner is known.

Ratings

How it works: Give each deck one number. Elo updates a rating after each game in proportion to how surprising the result was [GK] (https://en.wikipedia.org/wiki/Elo_rating_system [V]). Glicko-2 adds a rating deviation and a volatility, so a deck with few games has wide uncertainty [V] (http://www.glicko.net/glicko/glicko2.pdf). TrueSkill handles teams and free-for-all games with Bayesian factor graphs [GK] (https://en.wikipedia.org/wiki/TrueSkill). Weng and Lin’s approximations (the basis of OpenSkill) give similar online updates for multiplayer rankings [V] (https://jmlr.org/papers/v12/weng11a.html, https://github.com/vivekjoshy/openskill.py). Plackett-Luce models a full finishing order as a chain of softmax choices [V] (https://cran.r-project.org/package=PlackettLuce). Bradley-Terry is its two-player case [GK] (https://en.wikipedia.org/wiki/Bradley%E2%80%93Terry_model). Commander records usually keep only the winner. Cut Plackett-Luce to first place and you get the spike’s model: P(deck i wins) = exp(r_i) / sum over the pod of exp(r_j). This is a conditional logit (https://en.wikipedia.org/wiki/Conditional_logistic_regression [GK]). The spike fits it in one batch by maximum likelihood with a small L2 penalty, solved by Newton steps.

Where it has worked: Chess (Elo, Glicko), Xbox matchmaking (TrueSkill), and open-source game ladders (OpenSkill) [GK]. Arena and MTGO matchmaking use hidden ratings [GK].

Cost: Needs pod membership and the winner per game, plus several games per deck. Gives no card-level answer. A rating describes a deck with its pilot, and pilots are confounded with decks.

Validation: Fit on earlier games and score later ones by log loss against the ln(4) baseline (see Validation). On the fixture world it recovers the true deck order with Spearman 0.98 [V].

Card win rates

How it works: For each card, count the deck-seats whose deck holds it, and how many of those seats won. The baseline is not 0.5: in a pod of n the fair share is 1/n, so the spike sums expected = sum(1/seats) and shrinks toward it: rate = (wins + k*b) / (games + k) with b = expected/games and k = 20 prior games. A card in every deck rates exactly 1/seats [V]. 17Lands’ GIH WR (win rate of games where the card was in hand: opening hand or drawn) and IWD (improvement when drawn: GIH WR minus win rate when not drawn) refine this for Limited using in-game draw data [GK] (https://www.17lands.com/metrics_definitions; page is script-rendered, definitions not re-read).

Where it has worked: 17Lands draft data, where tens of thousands of games per card per set make GIH WR the community’s standard card-quality signal [GK]. EDHREC publishes inclusion rates, not win rates, which measure popularity rather than strength [GK] (https://edhrec.com).

Cost: Cheapest method: decklists plus winners. Its flaw is co-occurrence: a card that rides in strong decks inherits their wins. In the fixture world card_passenger adds nothing yet rates 0.284 against a 0.25 baseline [V], because it mostly sits beside card_strong (0.347 [V]). Filler cards that happen to sit in strong decks reach 0.40 [V].

Validation: Compare against a known-effect card (a synthetic world, or a card added to a fixed set of decks). Needs games_needed deck-seats per card for a given effect size (see Spike results).

Plus-minus

How it works: Adjusted plus-minus from basketball: regress each stint’s point margin on indicators of who was on the floor, so each player is credited net of teammates [V] (https://www.82games.com/ilardi1.htm, Ilardi 2007). Regularised APM (RAPM) adds a ridge penalty because teammates are collinear [GK] (https://en.wikipedia.org/wiki/Ridge_regression, https://en.wikipedia.org/wiki/Plus%E2%80%93minus_(sports)). For Commander the spike uses one row per deck-seat, y = won - 1/seats, X = 0/1 per card in the deck, ridge with no intercept.

Where it has worked: NBA player evaluation (APM, RAPM and later RPM variants) [GK]. Not known to be used for Magic cards in public [GK].

Cost: Same data as card win rates. Needs many distinct decks so cards are not perfectly collinear: two cards that always appear together cannot be separated by any amount of data. Shrinks rare cards to zero, which is safe but hides real effects until data piles up. No pair or synergy terms; adding them multiplies the parameter count.

Validation: In the fixture world it credits card_strong +0.133 per seat and gives card_passenger +0.0003 [V], where the raw win rate was fooled. A huge penalty (l2 = 1e6) shrinks all effects toward zero, as it should [V]. Real use needs cross-validated choice of l2.

Deck-stat regression

How it works: Same conditional logit as Ratings, but each deck is described by a stat vector (fast mana count, average mana value, interaction count, and so on) instead of an identity. It returns one weight per stat, which is logistic regression on deck stats in a pod setting [GK]. Because weights are shared, it scores decks it has never seen.

Where it has worked: Win-probability models in sport and esports regress outcomes on pre-game features [GK]. Commander’s “power level” talk and the bracket system’s game-changer list are informal versions: they name stats (fast mana, tutors, extra turns) thought to drive winning [V] (https://magic.wizards.com/en/news/announcements/introducing-commander-brackets-beta).

Cost: Needs decklists turned into stats, which is a feature-engineering job (SP8 territory). Stats correlate with each other and with pilot skill. Omitted stats bias the included ones.

Validation: On the fixture world it finds fast_mana = 1.01 (true card effect 1.2, diluted by per-deck noise) and avg_cmc = 0.18, which drives nothing [V]. Hold-out log loss on new decks is the real test.

Validation

  • Log loss: mean of -ln p(winner), p clipped at 1e-12. Baseline is mean ln(seats), ln 4 = 1.386 for 4-player pods. A proper scoring rule, so honest probabilities score best [GK].
  • Brier: mean over games of the sum over seats of (p - won)^2. Uniform guessing in a 4-pod scores 0.75 [V] (https://en.wikipedia.org/wiki/Brier_score).
  • Top-1: share of games where the highest-probability deck won. Chance is 0.25.
  • Time order: fit on earlier games, score later ones. Random splits leak deck and meta drift.
  • Sample size: games_needed(p0, p1) is the one-sample two-sided normal approximation (https://en.wikipedia.org/wiki/Sample_size_determination [GK]). It counts deck-seats, not pods.
  • Known-effect checks: synthetic worlds with planted cards (the fixture world) test whether a method can find a true effect and ignore a passenger. Every method here passes one.

Commander data

  • Four-player pods: the outcome is one winner out of four, so each game carries less information than a 1v1 result. Draws and “everybody conceded” outcomes are common and skipped.
  • 25% baseline: a card or deck is average at 1/seats, not 50%. Using 0.5 makes every card look bad. Pods of 3 or 5 need per-game baselines, which the spike computes.
  • Power-level matching: players choose pods by stated power level or bracket, so strong decks meet strong decks. Win rates then compress toward 25% and understate strength. Ratings and conditional logit correct for opponents only if pods mix across levels often enough to link them.
  • Selection bias: records come from players who log games: tournament players (cEDH), app users, or streamers. Their decks, pilots and metas differ from kitchen-table play, and they may log wins more than losses [GK] (https://en.wikipedia.org/wiki/Selection_bias).
  • Few public records: cEDH tournament standings exist (https://edhtop16.com [V]), but casual game outcomes with full decklists are rare in public. Seat and turn order are rarely recorded, and the spike ignores them (bias named, not modelled). SP1 owns the data inventory.

Verdict

Ranked for Commander, best first:

  1. Ratings (conditional logit or OpenSkill). Most reliable with winner-only pod data and the only one that adjusts for opponents. Needs: games linking decks across pods, several games per deck, and a pilot term if pilots vary. Gives deck strength only.
  2. Deck-stat regression. Scores new and unplayed decks, so it is the most useful bridge to a deckbuilder. Needs: good stat extraction from decklists, a few thousand games, and hold-out checks on unseen decks. Weights are only as good as the stats chosen.
  3. Plus-minus (ridge on cards). The right way to get card-level strength from outcomes, since it separates passengers from winners. Needs: many distinct decklists so cards decorrelate, hundreds of seats per card, and cross-validated l2. Pair terms only with far more data.
  4. Card win rates. Cheap and easy to explain, and fine as a screen with a 1/seats baseline and shrinkage. Needs: the same data as plus-minus. Never use alone: co-occurrence fools it, as the passenger card shows.

All four need time-ordered hold-out scoring against ln(4) before any number is trusted.

SP3 Deterministic strength models

Tags: [V] checked this session against the cited source; [GK] general knowledge, not re-checked. Engine sources read at Forge 7c34365 (2026-11-03), XMage 5a570a6 (2026-11-02), Magarena efa0aba (last commit 2023-04-24), shallow clones under ~/.cache/mtg-strength/src/. No engine code is copied here.

Q1 How deterministic models work

Three families. All map a card (or a board) to a number with fixed rules; none learn from play at run time.

rules-text. Parse oracle text into structured effects, then value the effects. Deckwright’s packages/roles reads each ability line, types it (activated, triggered, mode, cost, static) and matches effect rules, giving roles with a credit in [0, 1] and effect records with cost, speed, scope, repeat and beneficiary [V] (packages/roles/src/deckwright_roles/roles.py). Its packages/strength turns those effects into a value per job and context [V]. Engines also parse text, but into executable scripts rather than value: Forge card scripts (wiki) [V], and text-to-code models such as Latent Predictor Networks on MTG and Hearthstone cards (https://arxiv.org/abs/1603.06744) [V]. Full rules-text understanding is hard in principle: MTG is Turing complete (https://arxiv.org/abs/1904.09828) [V].

heuristic. Hand-weighted formulas over card fields: rarity, type, mana value, power and toughness, keywords, a removal flag. XMage’s draft bot uses this when a set has no rating file: rarity base + 2 x type weight + mana-cost score + 40 x removal, scaled by 0.5 [V] (Mage.Common/src/main/java/mage/cards/RateCard.java). The usual analogue is the Hearthstone “vanilla test” (stats per mana) [GK]. A second kind is the lookup list: Forge ships 193 per-set draft rank files and XMage 48 rating CSVs, many built from 17Lands data [V] (forge-gui/res/draft/rankings/, Utils/gen-draft-rates-17Lands.py).

engine-eval. A static evaluation of a game state used by search: sum life, cards and per-permanent values for each side. Forge, XMage and Magarena all do this (see the engine lines below). Chess engines are the canonical case: material plus positional terms (https://www.chessprogramming.org/Evaluation) [V].

Engine evaluation functions, from source: - Forge forge-ai/src/main/java/forge/ai/CreatureEvaluator.java [V]: creature value = 80, +20 if not a token, +15/power, +10/toughness, +5/mana value, then keyword terms (flying +10/power, deathtouch +25, indestructible +70, hexproof +35, defender minus 9/power + 40, and so on), activated abilities, mana ability +10. - Forge forge-ai/src/main/java/forge/ai/simulation/GameStateEvaluator.java [V]: board score = hand-card terms, 2 x team life minus 2 x opponent life, a mana-base term, plus each battlefield card’s value (creatures via the evaluator above, lands by colours produced, other permanents 50 + 30 x mana value). - XMage Mage.Server.Plugins/Mage.Player.AI/src/mage/player/ai/score/GameStateEvaluator2.java [V]: score = life score difference + permanent score difference + hand-size difference; win = 100,000,000. - XMage Mage.Server.Plugins/Mage.Player.AI/src/mage/player/ai/score/ArtificialScoringSystem.java [V]: life maps through a concave table (0 to 10,000 over 0 to 20 life, +100 per point above 20); creatures score 300 x power + 200 x toughness + ability scores; the card-definition value is a constant 3 marked TODO. - Magarena src/magic/ai/ArtificialScoringSystem.java [V]: the same life and poison tables and 300/200 power/toughness weights (XMage’s file is a port), but the card term uses a per-card value= field from each script, e.g. release/Magarena/scripts/Grizzly_Bears.txt has value=3.745 [V]. Those values came from Gatherer community ratings [GK].

Q2 Where they have worked

MTG. All three open-source engines ship playable AIs on hand-tuned evaluators and still use them as of November 2026 [V] (https://github.com/Card-Forge/forge, https://github.com/magefree/mage, https://github.com/magarena/magarena). They are good enough for casual play and draft bots, not strong play [GK]. XMage’s bot deliberately prefers 17Lands-derived file ratings over its own heuristic: “any bonuses on top make bot’s picks worse, checked on real human picks from 17Lands” [V] (RateCard.java). Deckwright uses a rules-text model in production for Commander role and strength advice [V].

Chess. Hand-written evaluation functions with tuned weights powered top engines for decades; Texel’s method fits those weights by logistic regression on game results (https://www.chessprogramming.org/Texel%27s_Tuning_Method) [V]. Stockfish moved to the learned NNUE evaluation (https://www.chessprogramming.org/NNUE, https://github.com/official-stockfish/Stockfish) [V], which is the lesson: deterministic structure plus fitted weights beat hand weights, and learned beat both [GK]. Classic piece values (1/3/3/5/9) are the material prior every evaluator starts from (https://en.wikipedia.org/wiki/Chess_piece_relative_value) [V].

Hearthstone and others. Community stat-per-mana formulas (vanilla test) were used to value cards before deck-tracker win rates; once played-win-rate data existed (HSReplay), it replaced them for strength [GK]. In Limited MTG the same happened with 17Lands GIH WR (https://www.17lands.com/card_ratings, https://www.17lands.com/metrics_definitions) [V].

Q3 Cost

Build. A heuristic is days of work: a formula over Scryfall fields (https://scryfall.com/docs/api) [V]; this session’s spike took about 100 lines (spike/build_scores.py) [V]. An engine evaluator rides on a full rules engine, which is years of work: Forge and XMage are large multi-module Java projects [V]. A rules-text parser is between: Deckwright’s packages/roles is about 5,000 lines of Python at parser version 2.29.0 [V].

Per new set. Heuristics need nothing unless new keywords appear. Rules-text parsers need new patterns for new mechanics; Deckwright tracks this as a parse coverage score per card [V] (roles.py _coverage). Engines must script every card before the evaluator sees it [GK]. Lookup lists need fresh 17Lands data each set [V].

Maintain. Weights drift silently; nothing in Forge or XMage re-fits them [V] (constants in source). Deckwright re-fits nine named priors by Bradley-Terry on its benchmark [V] (packages/strength/src/deckwright_strength/fit.py).

Q4 Accuracy

Engine evaluators. Validated against nothing measurable. Forge has direction-only unit tests (an allied permanent raises the score; a loss scores terminal) in forge-gui-desktop/src/test/java/forge/ai/simulation/GameStateEvaluatorTest.java [V]; XMage and Magarena have no evaluator tests by file name [V]. No repo compares evaluator output to outcomes. Accuracy unknown.

XMage heuristic. Its source states a regression over 8,622 cards from all 17Lands sets with “spearman 0.46” against file ratings [V] (RateCard.java). The target is 17Lands-derived ratings, not win rates, and the script is not in the repo, so the number is unverified.

Deckwright strength. Fitted file reports held-out pair agreement 0.881 and Kendall tau 0.642 on 344 hand-judged pairs over 153 cards [V] (packages/strength/src/deckwright_strength/data/fitted.json). The pairs are hand-judged, not outcomes.

Q5 Deckwright’s current method

Deckwright is a rules-text model in two layers. packages/roles (packages/roles/src/deckwright_roles/roles.py) parses oracle text into 15 function roles and 14 plan roles with credits in [0, 1]; opponent-decided effects earn half credit and a Scryfall-tag-only role earns 0.5 [V]. It predicts what a card does, not how strong it is. It was checked against Scryfall tagger tags as a recall report (packages/roles/src/deckwright_roles/recall.py, https://tagger.scryfall.com) and against anchor cards such as Sol Ring as ramp and Swords to Plowshares as removal (packages/roles/src/deckwright_roles/check_real.py) [V]. packages/strength then predicts a value and rank per card, job and context (bracket, players, strategy) from those effects only, never name, price or popularity [V]. It was checked against a frozen benchmark of hand-judged pairs and reference cases (packages/bench), with the numbers in Q4 [V]. Research note 14 found the earlier trunk ranked Pendant of Prosperity above Sol Ring and Overkill above every removal spell [V].

Gaps: - Never checked against outcome data; the benchmark is 344 hand-judged pairs, so it measures agreement with its authors. - Commander has no per-card win rates, so the Q4 spike cannot be repeated for its domain; SP1 must supply data. - Multiplayer and deck-interaction effects are priors, not measured; note 14 names per-event triggers firing once per turn. - Parse failures become value errors silently (Pendant, Overkill); coverage is tracked but not used to widen uncertainty. - No calibration: values are ranks per job, not win-probability units, so cross-job comparison is unvalidated.

Q6 Where deterministic models fit in a hybrid

Use them where they are strong: cheap, explainable, available on day one of a set. Three roles.

Prior. A deterministic score is a prior for a statistical model (SP2) that shrinks toward it when data is thin, as Texel tuning starts from hand values [V]. The spike says this prior is weak for raw heuristics (rho 0.13) and only rarity carries much signal, so prior strength should be low and fitted.

Features. Rules-text output (roles, effect scope, speed, cost) is the most useful part: it gives a statistical or learned model inputs that generalise to unseen cards. Deckwright’s effect records are already this [V].

Pruning for simulation. Engine evaluators exist to cut search: rank moves and stop rollouts early (SP4, SP5). Here they need only rank boards roughly, which is what Forge, XMage and Magarena use them for [V]. Card value should come from outcomes (17Lands in Limited, SP1 data in Commander), with deterministic scores as fallback and as explanation [GK].

SP4 Decomposed constrained simulation

Verdict: cheap, transparent and exact where it matters, but it measures consistency, not winning. It is a good feature layer for a statistical model (SP2) or a prior for RL (SP5). It cannot stand alone as a strength estimator until fitted to real outcomes (SP1).

How it works

Full Commander simulation needs a rules engine, four agents and politics. Decomposition skips that. It asks narrow questions a deck must answer, each cheap to compute (general knowledge):

  1. Can it cast its spells on time? (mana)
  2. Does it see the cards it needs? (draws)
  3. Can it assemble its win condition? (combos)
  4. Can it stop opponents? (interaction)

Each answer is a probability in [0, 1]. Questions with a closed form use the hypergeometric distribution. Questions with choices (which land to play, which spell to cast) use a constrained game: a goldfish (no opponent) played for a fixed number of turns, as in Karsten’s Commander curve model [1] and Deckwright’s goldfish simulators [3]. A combiner, fitted on decks with known outcomes, maps the feature vector to one strength score [9].

Pieces

Which pieces carry most of deck strength: speed of the win condition first, then interaction density, then mana consistency. Power-level discussion and cEDH practice treat “turn the deck can win” and “how much it can stop” as the main axes (general knowledge). In the spike’s synthetic outcomes, combo_t6 alone reaches held-out Spearman 0.77, the other two under 0.25. That is by construction of the fixture, so it only shows the method can find a dominant piece.

Piece Question Exact math or simulation
Mana, generic k lands by turn t Exact: hypergeometric [1][2]
Mana, colored lands seen can pay pips, one drop a turn Exact by enumerating land classes (multivariate hypergeometric); Monte Carlo is simpler [2]
Mana with rocks, ramp, MDFCs mana on turn t Simulation: sequencing matters [2][3]

Combo castable pieces seen and mana to cast them Simulation (joint mana and draw)
Interaction at least one answer by turn t Exact: hypergeometric

Exact pieces: anything that only asks “is card X among the first n cards”. The draw count rule sets n. Simulation is needed once choices or state enter: sequencing land drops with rocks, casting order, mulligan decisions, tutors, and anything about the opponents (general knowledge).

Combining pieces

Options, from simplest:

  • Hand weights. Points per feature, as power-level calculators do. No validation (general knowledge).
  • Linear least squares on features against win rate. Used in the spike (D4). Signs are readable; a negative weight on a known-good feature flags a bad feature or confounding [9].
  • Logistic / Bradley-Terry on pairwise or pod results, if outcomes are game-level (general knowledge).
  • Tree models catch interactions (combo speed only matters with protection), but need far more data than a 3-6 feature linear model (general knowledge).

The spike uses ordinary least squares with an intercept, solved by Gaussian elimination in pure Python. Fitted weights on the fixture: on_curve 0.149, interaction_t4 0.084, combo_t6 0.287; the generator’s true weights were 0.15, 0.10, 0.30.

Where it has worked

  • Land counts and mana bases. Karsten’s hypergeometric source tables and Commander curve simulator are the standard reference; Deckwright reproduced his model game for game [1][3].
  • Available-mana simulation beyond the hypergeometric, including rocks [2]; landlord does the same for 60-card decks [10].
  • Deckwright goldfish simulators: seeded land-only goldfish for colored untapped mana, and a generic-mana goldfish with rocks, used as consistency checks in its strength report [3].
  • Constrained games in research: Monte Carlo search over determinized Magic games with simplified rules [5]; Forge’s AI plays full games but is weak for strength estimation [4].
  • Card-level outcome decomposition: 17lands “game in hand win rate” credits single cards with outcomes in Limited, which shows feature-to-outcome fitting at scale [9].

Nowhere found: a published Commander strength model built from decomposed pieces and validated against pod outcomes. That gap is the question SP1 data would answer (general knowledge).

Cost

  • Exact pieces: microseconds per feature. A full profile of a 99-card deck takes under 10 ms in the spike (exact formulas) (general knowledge, measured below).
  • Monte Carlo: 20,000 trials of one piece take about 50 ms in pure Python. A full goldfish with rocks and sequencing is about 1 s per 200,000 games per deck in vectorized numpy [3].
  • Build: pieces are days of work each; a goldfish with ramp and tutors is weeks [3].
  • Data: the combiner needs labeled decks. That cost dominates (see Validation).

Validation

How the combined score is checked: fit weights on training decks, score held-out decks, report Spearman rank correlation between score and observed win rate, and compare with the best single feature. A combiner that does not beat its best feature adds nothing [9].

How much outcome data: two noise sources (general knowledge, binomial arithmetic).

  • Per-deck win rate noise. In 4-seat pods the base rate is 0.25. With g games the standard error is sqrt(0.1875 / g): 0.043 at 100 games, 0.019 at 500. Real deck-to-deck spread is likely 0.05-0.15, so each deck needs a few hundred games before its label ranks reliably.
  • Number of decks. The standard error of Spearman is about 1/sqrt(n - 1) at rho near 0. Telling rho 0.7 from 0.5 needs about 60-100 held-out decks; the fixture uses 40.
  • Confounding. Pilot skill and pod matching move win rate as much as the deck. Without pilot control, a fitted weight can reflect who plays a deck, not the deck (general knowledge).

So: roughly 100+ decks with 200+ logged games each, or a ranking signal (tiers, tournament results) used as an ordinal target. SP1 owns whether such data exists.

Self-play RL for Commander strength (SP5)

Research only. No agent, environment or training run was built. Numbers come from spike/rl_cost.py applied to SP7’s measured forge-speed.json [10].

How it works

  • An agent plays copies of itself (or a pool of past selves) and learns a policy (what to do) and a value (who will win) from the results [1][8].
  • For strength measurement, a well-trained agent piloting a deck gives a deck’s ceiling win rate, not the autopilot floor that scripted AI gives. MageZero showed this on XMage: one deck rose from 16% to 66% against minimax bots [6].
  • Card strength then follows by ablation: swap a card, retrain or fine-tune, re-measure (general knowledge).

Algorithms

  • MCTS + network (AlphaZero family) [1]: search guided by a policy/value net. Best fit for Magic’s long turns and huge, structured action space. MageZero already runs it on XMage [6].
  • ISMCTS [7]: MCTS over information sets, sampling hidden cards per iteration. Ensemble determinization was studied on Magic itself [11]. Cheap, no training; a strong baseline and the search half of any learned agent.
  • Self-play PPO [8]: model-free policy gradient. Simple and multiplayer-friendly (OpenAI Five [12]), but sample-hungry; with Forge at hundreds of games/hour it would not converge (see Compute cost).
  • CFR-style search (ReBeL, Student of Games) [3][4]: sound for hidden information, with guarantees only in two-player zero-sum. Public belief states over a 99-card library and hands are far larger than poker’s; not practical here (general knowledge).
  • Fit: AlphaZero-style MCTS with ISMCTS-style sampling of hidden cards, trained per deck against a pool, as MageZero does [6][7]. PPO only if a fast engine exists.

Hidden information

  • Determinization: sample opponents’ hands and library orders consistent with what is known, search each sample, vote. Simple but suffers strategy fusion and leaks: MageZero’s search sees future draws, so its numbers flatter reactive decks [6][7].
  • Information sets (ISMCTS): one tree over what the acting player can observe; removes most leakage at some cost in strength per simulation [7].
  • Belief states: ReBeL and Student of Games search over public belief states [3][4]; the state for Commander (four 99-card libraries, hidden hands) is intractable without heavy abstraction.
  • Recommendation: information-set sampling at search time, network inputs without hidden cards (MageZero already strips them from the net) [6][7].

Multiplayer

  • At 2 seats the game is zero-sum and self-play has equilibrium guarantees (ReBeL, Student of Games) [3][4]. Every extra seat breaks them.
  • At 3 to 6 seats the game is non-zero-sum between subsets: no Nash guarantee holds, yet Pluribus still beat pros at 6-player poker with self-play plus search [2].
  • Kingmaking: a losing player decides who wins. Win-rate labels then depend on table behaviour, not deck strength alone (general knowledge).
  • Politics: deals, threat assessment and “attack the leader”. CICERO needed human data and language to play Diplomacy’s 7-player cooperation well; pure self-play learned strategies humans would not follow [5].
  • As seats grow: games get longer (D2, linear in this model), the action space and hidden state grow, credit assignment gets noisier, and the base win rate falls to 1/seats, so evaluation needs more games per deck to see the same gap (see Validation) [2] (general knowledge).
  • MageZero is two-player only; its graph encoding keeps the player node generic for later [6].

Basic guidance

Intake Q4: pure self-play or bootstrap from existing play? - Pure self-play from random play works in perfect-information two-player games (AlphaZero) [1], but random Magic play rarely finishes a Commander game in a 120 s clock (general knowledge). - Bootstrap from Forge AI: imitate Forge’s scripted AI first, then improve by self-play. AlphaStar bootstrapped from human replays then used league self-play [9]; MageZero starts against minimax bots and adds an opponent pool [6]. - Human data: CICERO regularized toward human play (piKL) to stay compatible with people [5]. Commander logs with decisions are not public at scale (general knowledge). - Recommendation: bootstrap from Forge AI and keep a fixed Forge-AI opponent seat as an anchor; pure self-play at 4+ seats risks table conventions no human table shares [5][9].

Engine and environment

  • Wrap Forge: best rules coverage and four-player Commander. Measured: 264.5 games/hour at 8 workers, 4 seats, clock 120 s (forge-speed.json) [10]. Many games hit the clock, so real game time is longer and this rate is an upper bound [10].
  • Wrap XMage: MageZero’s route, with a working JVM-to-Python bridge (HTTP + msgpack) and about 800 two-player games/hour on 16 threads [6].
  • Build a fast engine: AlphaZero-class training needs millions of games [1]; with Forge that is months (see Compute cost). A rules engine covering Commander is a multi-year effort; a 50x speedup is an assumption, not a measurement (D4, general knowledge).
  • Learned agents add network inference per decision; an MCTS budget of hundreds of simulations per move multiplies engine cost again [6] (general knowledge). The cost table ignores this, so it is a floor.

Where it has worked

  • AlphaZero [1]: chess, shogi, Go from pure self-play; perfect information, two players.
  • Pluribus [2]: six-player no-limit poker beat pros; hidden information, multiplayer, CPU only.
  • ReBeL / Student of Games [3][4]: one algorithm for perfect and imperfect information, two-player.
  • CICERO [5]: human-level 7-player Diplomacy with negotiation; needed human data.
  • AlphaStar / OpenAI Five [9][12]: huge action spaces and hidden state, at enormous compute.
  • MageZero [6]: AlphaZero-style per-deck agents on XMage; two-player Magic, Commander weakly.
  • Magic MCTS research [11]: determinized MCTS played Magic better than rule-based play.
  • Nothing has shown learned agents for four-player Commander (general knowledge).

Validation

  • Agent win rates become deck strength by playing each deck many times at a fixed table of reference opponents (a Forge-AI anchor plus agents) and reading its win rate against 1/seats [2][6].
  • Card strength: win-rate change when a card is swapped, under the same agents (general knowledge).
  • Sample size: games_for_ci with the normal approximation; games_to_rank needs each deck’s rate within half the gap (general knowledge).
  • games per deck to separate 5 points at 4 seats: 1153
  • At 2 seats it is 1,537 and at 6 seats 854 games. At 661 games/h (4 seats, 20 workers) that is about 1.7 h per deck in Forge [10].
  • Check against SP1 outcome data (real tables) and SP2 statistics; agent ceilings should rank decks the same way human win rates do, or the method fails (general knowledge).

Verdict

Defer. Learned self-play agents are the only method that measures a deck’s ceiling under skilled play, and per-deck AlphaZero-style training is affordable on Forge (15-45 h per deck, 2 to 6 seats) [6][10]. But a general agent across decks is months on Forge, hidden information still leaks, kingmaking and politics make multiplayer labels noisy, and nothing has shown it for four-player Commander [2][5]. Build it only if (1) cheaper methods (SP2-SP4) leave a validated gap for high-skill decks, (2) SP1 provides outcome data to check agent rankings, and (3) either per-deck scope is accepted or a 50x-faster engine exists. Start from MageZero’s design on a duel, with ISMCTS sampling and a Forge-AI anchor seat [6][7].

SP7 Open-source engines and AI

Notes, each read from pinned source: forge.md, xmage.md, magarena.md, magezero.md, argentum.md. Speed: forge-speed.md; record in forge-speed.json (measured on the host, 2026-11-03). Tool: spikes/sp7/forge_speed.py.

Lessons

For a strength estimator (ranked): 1. Engine win rates measure deck x pilot. Every engine AI here is heuristic or shallow search, strongest with linear aggro and weakest with combo and reactive decks (forge.md, magezero.md). Treat engine win rates as a biased feature, not ground truth. 2. Check what the pilot can see. XMage’s default bot and Argentum’s bot use the full hidden state; Forge’s sim path has small per-card peeks. Peeking inflates interactive decks’ win rates (xmage.md, argentum.md). 3. Pin the build. Forge’s AI changed a lot after 2.0.15; numbers compare only within one tag (forge.md). 4. Forge scores clock-capped games as wins, not draws. Raise the clock or flag capped games, or slow decks get noisy wins (forge-speed.md). 5. Magarena’s DeckStrCal (two decks, fixed AI, N games) is the simplest estimator template; its honest/cheat AI pairs show how to measure the peeking bias (magarena.md).

For an RL environment (ranked): 1. Immutable state with cheap fork (Argentum) beats whole-game copies (Forge, XMage) for search speed. 2. Mask hidden zones in the observation by default (Argentum gym). Determinized search still leaks (magezero.md). 3. Bridge over local HTTP with batched inference (MageZero) rather than linking into a GPL JVM. 4. Forge is the only engine with a working four-player Commander AI today; a PlayerController socket bridge covers about 110 decision methods, with heuristic fallback per method. 5. Deck-local agents (MageZero) are proven in 1v1 at about 800 games/hour; four-player Commander costs more.

Open questions answered

Q1

Forge 2.0.15, four-player Commander, 8 workers, 120 s clock: 264.5 games/hour (32 games, one precon x4; median 104 s). This is an upper bound: capped games count as wins and many games hit the clock. About 3.8 h per 1,000 games (forge-speed.md).

Q2

PlayerController (abstract, about 110 methods) is the hook; PlayerControllerAi implements it. In sim, simulation is off, so the heuristic path runs. It is mostly honest but peeks in ChangeZoneAi, chooseCardName and ClashAi. At the tag the simulation path copies real hidden cards (PRUNE_HIDDEN_INFO = false).

Q3

MageZero’s Java side calls a Python Flask/waitress server on 127.0.0.1 over HTTP with msgpack and batched GPU inference. It supports Commander only as two-player (game_mode: commander, player_a/player_b); multiplayer is unsupported per its FAQ.

Q4

XMage’s default bot is “Computer - mad” (ComputerPlayer7 proxy, minimax, 5,000-node cap) per config.xml. It searches full game copies, so it sees hidden cards. Four-player behaviour was not tested (D6: read, not run).

Q5

Forge is GPL-3.0: an agent linked into the JVM becomes a GPL derived work. A separate process talking over a socket keeps our code under our own licence (general knowledge, not legal advice). XMage, MageZero and Argentum are MIT.

  • Cost: about 1,000 games per generation and many generations per deck. At 800 games/hour that is hours per deck, in 1v1. Four-player Commander would be slower.
  • HTTP plus msgpack plus server-side batching is a proven, simple bridge pattern for a JVM engine.
  • Determinized search still leaks; a strength number from such agents is optimistic for reactive decks.

  • Kotlin, Gradle. rules-engine/ (pure rules), ai/ (bots), gym/, gym-server/, gym-trainer/ (RL), game-server/ (Spring Boot), web-client/ (README.md).
  • AI: ai/src/main/kotlin/com/wingedsheep/ai/engine/AIPlayer.kt, Searcher.kt, Strategist.kt, CombatAdvisor.kt, evaluation/BoardEvaluator.kt, set-specific advisor/modules/*AdvisorModule.kt.

Decision method

  • Searcher.kt: alpha-beta search with adaptive depth measured in priority passes; close decisions search deeper, obvious ones stay 1-ply; node cap from config. Leaves scored by BoardEvaluator.kt.
  • Per-card and per-set hints via advisor modules (Bloomburrow, Onslaught in EngineAiPlayerController.kt).
  • An LLM-driven controller exists as an alternative bot (llm/ package).
  • gym-trainer/src/main/kotlin/com/wingedsheep/gym/trainer/search/AlphaZeroSearch.kt and MctsNode.kt: JVM-side AlphaZero MCTS for self-play.

Hidden information

  • The built-in bot peeks: EngineAiPlayerController.kt says it needs “the real (unmasked) GameState” to simulate.
  • The gym is honest by default: TrainingObservation masks opponent hand and libraries and reports only zone sizes for hidden zones (gym/README.md).
  • So the RL interface is clean; the heuristic baseline is not.

Multiplayer and Commander

  • Free-for-all for 2-6 players (CR 806) in the server (README.md).
  • Commander rules in the engine: rules-engine/.../sba/player/CommanderDamageLossCheck.kt, CommanderZoneChoiceCheck.kt, state/components/identity/CommanderComponent.kt.
  • The searcher only models a reply when there is a sole opponent (Searcher.kt uses soleOpponent); with three opponents it falls back to 1-ply evaluation. Weak multiplayer AI.
  • Card pool is set-by-set (mtg-sets/, card-implementation-progress.html); a full precon may not be legal yet.

Headless use and speed

  • gym/README.md: GameEnvironment with reset/step/observe/fork; O(1) fork because GameState is immutable; MultiEnvService runs many envs and steps them in parallel. gym-server/README.md: HTTP transport for Python.
  • Speed harness exists (ai/src/test/kotlin/com/wingedsheep/ai/engine/GameBenchmark.kt prints games/sec); no published numbers. Not run (D6).

Learning-agent hook

  • Best-designed hook of the five: a Gymnasium-style env with legal-action enumeration, masking, snapshot/restore, a schema hash, and pluggable featurizers and evaluators in gym-trainer/.../spi/ (Evaluator.kt, StateFeaturizer.kt, RemoteHttpEvaluator.kt).

Lessons

  • Immutable state plus O(1) fork is the property that makes search and RL cheap; Forge and XMage copy whole games.
  • Masked observations by default is the right contract for an honest agent (gym/README.md); copy the idea, not the code.
  • Card coverage, not AI, is the limit for Commander: check precon legality before relying on it.
  • Track upstream wingedsheep, not the rwaldron fork.
